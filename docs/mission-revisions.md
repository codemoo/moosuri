# Change the conditions of a paused mission

In **Missions**, pause a stable one-off mission, choose **조건과 확인 기준 변경**, edit the task, conditions and checks, then save **새 조건으로 다시 계획**. Saving itself authorizes the revised task within the originally admitted read tools; no additional approval dialog is added. The task replans under the new criteria. Additive **추가 지시** remains separate and does not change checks.

The original request and each accepted criteria version remain in **처음 요청과 조건 변경 이력**. The active request, plan and result refer to the latest criteria. Existing source-quote/required-output checks remain when editing the simpler review/exact-number fields; the API can explicitly replace typed checks. Semantic conditions continue to require owner review, and selected machine checks do not prove a general semantic outcome. The original immutable create payload remains the original request identity.

Editing does not increase model/tool allowance, the original deadline/expiry or the total two allowed repairs. It cannot turn a spent budget into a fresh execution window. Old accounting/step records remain, but superseded plans, unentered tools, receipt references, late leases and candidate proposals cannot execute or satisfy the new criteria. Previous additive steering is archived by existing control history and cleared from the new active plan. At most eight criteria edits are supported.

Only stable paused one-off missions are editable. Unknown or started dispatches, recurring mission occurrences, expiry, source/model/skill withdrawal, stale account epoch and restore quarantine are rejected. Original model/tools/Google account pins and execution mode stay fixed. A new Gmail/Calendar domain needs a new mission if it was not originally admitted; recognized unsupported send/browser/vault/shell requests and unavailable explicit public-web reads are rejected. Conservative language checks do not establish understanding of arbitrary prose. The closed typed tool/profile checks remain the actual execution boundary. No mail sending, drafts, Calendar writes, browser/vault/shell capability or budget extension is added.

The form retains inputs after failure. An uncertain retry reuses the exact operation UUID, payload and original revision; changing fields starts a different request. A known conflict requires reviewing current state rather than silently applying the edit to a newer mission. Account changes unmount the private form and use the existing scoped request cancellation.

The authenticated endpoint is `PUT /api/v1/missions/{id}/acceptance`, with `request_id`, `expected_revision`, `task`, `constraints` and `checks`. Execution mode/provider/tool scope are deliberately not update fields. Existing records without criteria history retain the original request/revision1 behavior. Schema52 stores private acceptance snapshots separately from original missions and scopes them to tenant/mission. Explicit mission deletion and account erasure purge them. Full SQLite snapshots retain the history while restore quarantines all unfinished authority. The offline forward restore applies both reminder schema51 and acceptance schema52; it does not reactivate either grant.

See [existing mission boundaries](missions.md) and [verification](reviews/2026-11-15-mission-revisions.md). This unit is bounded read/local mission acceptance, not full F27 or real-model/provider quality certification.
