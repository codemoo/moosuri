# 맡긴 일

사이드바의 **맡긴 일**에서 일회성 요청, 지켜야 할 조건과 확인할 내용을 직접 입력한다.
대화의 명시적 위임은 아래 schema29 경로로 저장한다. 자료 속 지시는 실행 권한이 아니다. 기본값인 ‘창을 닫거나 로그아웃해도
계속’은 이 요청에 한한 명시적 실행 허용이다. 이를 끄면 요청 당시의 실제 로그인 세션이
유효한 동안만 실행한다. 관리자는 다른 사용자의 결과를 읽거나 제어할 수 없다.

현재 범위는 보관 자료·기억 검색/읽기, 허용한 지침 스킬 읽기, 정확한 소수 계산,
설치에서 설정한 공개 HTTP 읽기/검색, 업무에 명시한 연결 Gmail·기본 Calendar 읽기다. 메일 발송·초안·Calendar 변경·브라우저·볼트·임의 코드·외부 쓰기는
실행하지 않는다. 해당 도구를 요구하면 지원하지 않는 작업으로 남기고 무의미한 수정을 반복하지 않는다. 결과는 해당 사용자의 맡긴 일 기록 안에 저장한다.

일반적인 내용·의미 검토는 ‘일부 결과 · 검토 필요’로 남는다. 모델의 완료 선언은 증명이
아니다. API의 정확한 소수 결과, 원문 ID·revision·인용문, 출력 형식 조건은 현재 실행의
실제 완료 영수증과 대조한다. 출력 형식 조건은 내용의 의미를 증명하지 않는다.
자연어 조건을 적으면 양식은 `user_review`를 포함한다. API에서 이를 생략해도 서버가
추가 조건의 검토를 요구하며 원래 요청은 바꾸지 않는다. 기계 검사가 모두 통과하면
추가 모델 수정을 반복하지 않고 결과를 검토 필요로 남긴다. 조건이 없는 계산 확인은
정확한 값의 영수증·출력이 일치할 때 선택한 확인 기준을 통과한 것으로 표시한다.

계획은 최대 다섯 단계다. 계획과 실행·검증·최대 두 번의 수정은 모델 여섯 번, 도구 열두 번의
같은 실행 한도를 사용한다. 요청 당시부터 하루가 지나면 만료된다. 정지·재시작·추가 지시는
시간이나 한도를 늘리지 않는다. 한 사용자당 진행/정지 중인 일은 하나, 설치 전체는 최대
열여섯 개를 기다릴 수 있고 동시에 실행하는 맡긴 일은 하나다. 일반 대화에 실행 자리를 남긴다.

잠시 멈춘 뒤 안정적으로 완료된 읽기/계산 결과는 이어서 사용할 수 있다. 모델·공개 HTTP 요청이
이미 시작된 순간 멈추거나 프로세스를 잃으면 그 요청을 자동 재실행하지 않는다. 응답이 이미 완료된 계획·결과 제안은 모델 영수증과 같은 트랜잭션에 명시적 자료로 보관하며, 재시작 때 그 자료를 확인하므로 같은 제안을 다시 요청하지 않는다. 결과 불명
안내를 확인하고 새 일로 맡긴다. 정지 상태에서 추가 지시를 할 수 있지만 처음 요청·조건·확인
기준은 변경하지 않는다. 취소는 이후 실행을 막으며 이미 발생한 사용량 영수증은 남는다.
자료·스킬·모델 연결 철회는 관련 결과와 실행 허용을 무효화한다. 계정 정지·인증 세대 변경 후
자동 재허용하지 않는다. 복원한 미완료 작업은 격리하고 새 요청을 받아야 한다.

API는 `POST/GET /api/v1/missions`, `POST /api/v1/missions/{id}/control`,
`DELETE /api/v1/missions/{id}`다. 모든 요청은 실제 세션과 `X-Moosuri-Account`를 검사한다.
생성 UUID를 재시도하면 같은 요청을 찾고 다른 내용이면 충돌한다. 제어는 UUID와 revision CAS를
사용한다. 제어 재시도는 현재의 철회 상태를 반영하여 과거 비공개 결과를 다시 노출하지 않는다.
삭제는 기존 파괴적 작업 저널에 영구 기록하며 재시도·복원으로 삭제한 결과를 되살리지 않는다.

일회성 단위 자체에는 반복 예약된 복합 작업, 변경점 비교, 대화에서 작업 자동 추출, 실행 범위 확장,
브라우저 읽기, 의미 판단 자동 완료가 포함되지 않는다. F27 전체 완료를 의미하지 않는다.

## Acknowledged recovery and control retries

A stable acknowledged final proposal can finish local receipt verification after restart even at exactly6model calls or12tool calls. This exception requires the latest completed non-planning proposal and no unresolved tool/unknown dispatch. It does not authorize another dispatch or reset any original budget, deadline, account/provider/epoch, withdrawal or monotonic-clock fence. Ordinary chat retry admission is unchanged.

An uncertain owner control retains its UUID/payload only for an explicit retry of the same mission and exact action. Polling/current-state reads retire stale control revisions; a later Cancel or another card/instruction gets its own current revision and fresh UUID. A racing CAS rejection reconciles state and retries only that newly requested intent once. A failed current-state read stops the control instead of replaying an older action. No additional approval UI is introduced.

Stable mission controls and restarts cannot strand execution at the shared chat attempt32 boundary. Within the same writer transaction, mission continuations retire the old run lease and use a fresh nonce on claim; no old run/step capability can change the resumed result. Step accounting receipts remain available for late usage, and original model/tool/time limits remain unchanged. Ordinary chat retries retain their existing limit. Unknown dispatches never enter this path.

## 명시적으로 예약하는 읽기 업무

**예약해서 맡기기**에서 일·조건·계산 확인값과 한 번/간격/매일/매주 시간을 직접 저장한다.
저장한 업무 본문·확인 기준·당시 검증된 모델/effort·읽기 범위는 고정된다. 시간 규칙과
이름은 바꿀 수 있으며 업무 내용이나 모델을 바꾸려면 새 예약으로 저장한다. 메일 발송·초안·Calendar 변경·브라우저·
볼트·외부 쓰기는 예약할 수 없다. 직접 양식의 권한은 실제 저장 요청에서 나온다.
아래 대화 경로는 현재 사용자의 명시적 요청만 해석하며 자료나 일반 모델 출력은 권한이 아니다.

기존 알림과 같은 IANA/DST gap/fold·UTC anchor·latest-only 정책을 사용한다.5초마다
DB만 확인하며 유휴 모델 호출은 없다. 한 회차당 실제 맡긴 일 하나만 원자적으로 저장하고
기존 사용자당 하나·전체16개 대기·동시 미션 하나 한도를 유지한다. 바쁜 사용자의 예약이
다른 사용자의 접수를 가리지 않도록 소유자별 한 회차를 공정 순서로 확인한다. 회차 한도는
예정 UTC부터 최대 하루와 설정한 유효기간의 이른 쪽이다. 늦게 접수하거나 재시도해도
시간·모델/도구 한도를 새로 주지 않는다. 오래된 일회 예약은 만료 기록만 남긴다.

예약 정지·시간 변경·삭제는 미완료 하위 실행을 은퇴시킨다. 시작된 모델/HTTP가 있으면
결과 불명으로 남기며 재실행하지 않는다. 재개는 다음 미래 회차부터다. 별도 실행 허용은
로그아웃 후에도 남지만 계정 세대 변경·정지·연결 철회에는 자동 재허용하지 않는다. 복원은
예약을 정지하고 미완료 실행을 격리한다. 계정 재등록만으로 예약이 다시 켜지지 않는다.

각 회차의 실제 결과·근거는 맡긴 일 기록에 남는다. 소식함에는 고정된 실행 상태와 해당
기록 링크만 보관하며 업무 본문·출력·출처 제목/인용문을 복사하지 않는다. 근거 철회 뒤
링크를 열어도 철회한 결과가 다시 나타나지 않는다. 기존 Push 정책은 별도 기기 설정을 따른다.

‘정확히 같은 확인 결과는 소식함 알림 생략’은 **성공한 본문과 실제 계산/원문 영수증의
정확한 일치**만 비교한다. 원문 ID·revision·반환 본문은 비교하고 호출/단계 ID·관측 시간은
제외한다. 문장이 달라지면 의미가 같아도 알림을 남긴다. 검색·기억·웹·스킬 근거는 현재
비교하지 않으며 항상 알린다. 검토 필요·실패·결과 불명·철회된 이전 결과는 생략 기준이
아니다. 바로 이전 회차와 같은 예약 revision/인증 세대 안에서만 비교하므로 정지/재개·편집
후 첫 결과도 알린다. 생략한 경우에도 실행 기록과 정확한 일치 상태는 남긴다.

API는 `/api/v1/recurring-missions`(GET/POST), `/{id}`(PUT 시간 규칙),
`/{id}/control`(POST pause/resume/revoke)이다. 일반 `/schedules`와 대화 알림 선택/제어는
이 예약을 읽거나 바꾸거나 고정 알림으로 발행할 수 없다. 회차20개·시간 이력/건너뛴 범위
각50개를 반환한다. 대화의 읽기 업무 등록은 아래 schema29 경로를 따른다. 일반적인 의미상
변경 비교는 후속 범위이며 F29/F30/F31 전체 품질 완료 주장이 아니다.

통합된 schema26/27/28과 실제 화면 검증은 [예약 업무 검증 기록](reviews/2026-11-13-recurring-missions.md)을 따른다.

## 대화로 맡기고 제어하기 · schema29

‘매일 아침9시에 공개 뉴스 찾아서 요약해 줘’, ‘시간 걸려도 공개 자료 비교하는 일
맡아서 해 줘’, ‘Morning digest 업무 잠깐 멈춰줘’처럼 현재 요청을 해석하는 경로를
연결했다. 명확한 요청은 별도 승인 화면 없이 실제 업무/예약으로 저장한다. 월요일만
말하고 시각을 빼면 실행할 시간을 묻는다. 대상을 확정할 수 없으면 현재 소유한 업무 카드를
선택하고 대상만 답해 원래의 제한된 요청을 마칠 수 있다. 예약 이름·일/계산 본문 전체와 정확히
일치하는 이름이나 선택한 대상/revision을 사용하며 비슷한 이름을 모델이 만들어 선택하지 않는다.

고정 알림의 ‘...라고 알려줘’/‘remind me ... to’는 여전히 문구를 그대로 저장한다.
실제 조사/요약 예약과 구별한다. 일반 메시지에는 새 분류 모델 호출이 없고, 시간·위임·제어
후보에서만 현재 메시지와 저장한 시간대/기준 시각을 별도 모델 호출 하나로 해석한다.
대화 이력·자료·첨부·모델 출력은 업무 생성 권한이 아니다. 해석 결과는 실제 모델 영수증과
동시에 저장하고, 재시작/같은 요청 재시도에서 다시 분류하거나 기본 모델로 바꾸지 않는다.

내용 검증은 직접 검토 기준을 기본으로 저장한다. 해석 모델이 소수 정답·원문 ID/revision을
만들어 완료 기준으로 넣지 않는다. 메일/브라우저/볼트 쓰기·외부 발송은 지원 범위를 늘리지
않았다. 실제 결과는 기존 맡긴 일/소식함에서 확인하며 저장 확인문은 완료 선언이 아니다.
현재 대화의 첨부 또는 이어받은 첨부가 있으면 이 생성 경로는 사용하지 않는다.

현재 지원하는 제어는 한 번 맡긴 일의 정지/재개/취소/추가 지시와 반복 예약의
정지/재개/취소(예약 철회)/시간 변경이다. 이력 삭제·예약 본문/모델/변경점 정책 교체와
대화에서 현재 세션만 실행 모드 지정은 이 단위에 포함하지 않는다. 기존 직접 양식은 유지한다.
휴일/영업일·이벤트 트리거·‘다음 주부터’ 같은 시작 범위와 모호한 오전/오후를 임의로
추론하지 않는다. 명확한 시각은 기존 IANA/DST/UTC 엔진으로 계산한다.

이미 저장한 독립 업무는 원래 대화를 지워도 취소하지 않는다. 저장 전 대화/계정 권한을
잃으면 실행 허용을 만들지 않는다. 접수 때의 원래 세션 digest/인증 세대를 계획에 고정하며,
로그아웃·만료·세대 변경 뒤 새 로그인으로 기존 미적용 계획을 재시도해도 되살리지 않는다.
현재 로그인에서 새로 말한 요청은 별도로 접수할 수 있다. 복원한 미적용 해석 계획은 격리되며
계정 재등록만으로 다시 적용하지 않는다. 소식에는 원문/결과를 복사하지 않는다.

시각 인용문에 명시된 시·분·오전/오후·요일 집합·오늘/내일/날짜를 저장한 기준 시각과
대조한다. 현재 요청에 명시한 UTC/IANA 시간대가 브라우저 시간대보다 우선하며, 해석할 수
없는 offset/약어는 다시 묻는다. 자정·정오·한국어 분 표현 등 검증하는 범위 밖의 표현은
명확히 다시 요청해야 할 수 있다. 선택한 대상과 명시한 전체 이름이 다르면 어느 쪽도
변경하지 않고 현재 업무 카드를 보여 준다. 이름이 같아도 대상 revision이 바뀌면 다시 선택한다.

대상 재개/추가 지시 전에 원래 요청·소유자·대상 revision을 확인하고, 만료/근거 철회의
실행 guard 전이만 먼저 확정한다. 이후 작업 변경·영수증·확인문 저장은 함께 커밋하거나
함께 되돌린다. 확인문 저장이 실패해도 이미 확인한 대상 만료·철회는 되살아나지 않는다.
시간 예산 만료·대상 권한 철회·접수 용량 부족은 구별해서 알린다.

현재 합성 시험은 호출/권한/저장/재시도 경로의 검증이다. 자연어 이해 정확도나 실제 모델
응답 속도 점수를 뜻하지 않는다. 인용문 검사는 현재 메시지에서 왔음을 확인할 뿐 모든
문장의 의미상 권한을 증명하지 않는다. 별도 고정 어휘 사례·부정/인용 공격 사례와 실제 모델
평가는 구별하며 실모델 비용/실기기 검증은 이 단위에서 수행하지 않았다. 첫 독립 cue 평가의
13개 후보 중 11개 진입·2개 누락과 일반 2개 우회 결과를 보존한다. 그 문구는 이후 작업자에게
노출되어 회귀 사례가 되었으며, 별도로 고정한 새 후보4개도 처음에는2개만 진입했다. 이를 수정한 뒤13/13·4/4를
통과했지만 모두 노출된 회귀 사례이므로 새 unseen 점수가 아니다. cue 진입은 자연어 의미
정확도 점수가 아니다. [독립 검토와 통합 검증](reviews/2026-11-13-conversational-missions.md)을 따른다.

대상을 선택하지 않았고 이름 인용도 빠진 제어는, 소유한 업무가 하나라도 임의로 적용하지 않는다.
현재 업무 카드를 선택하거나 전체 이름을 포함해 다시 요청하면 된다. ISO 날짜와 시각 사이의
공백을 없애 날짜를 시각으로 합치지 않으며 명시된 날짜를 반복 예약으로 바꾸지 않는다.

## 요청의 빠진 값 이어받기

명시적으로 맡긴 읽기 업무의 날짜/시각·대상·본문이 빠졌다면 확인 질문 다음 메시지에서
그 값만 답할 수 있다. 예를 들어 `every Monday summarize public paper updates` 다음의
`at 9AM`은 원래의 월요일·업무 본문을 유지한 예약 한 개로 저장한다. Calendar와 같은
요청 continuation 저장 경로를 사용하며, 일반 대화 이력을 해석 권한에 넣지 않는다.
부분 typed 초안의 action·이미 명시한 본문/조건/시각/대상은 고정하고 새 인용값은 현재 실제
답변에서 확인한다. 시각 인용문은 짧은 현재 답변만 담아도 원래 전체 요청의 요일·날짜를
별도로 다시 검사하므로 긴 업무 본문을 시간 인용문에 복사하지 않는다. 단어 하나의 답변도 이미 대기 중인 제한된 요청이 있어야 분류 후보가 된다.

바로 앞의 완료된 확인 질문, 같은 대화·소유자·로그인 세션/인증 세대·검증 모델 선택에서
30분 동안 최대 네 번의 답변만 이어진다. 원래 시간 기준과 선택한 대상 revision을 유지한다.
다른 대화·중간의 일반 대화·로그아웃/철회·복원은 미완료 요청을 자동 재허용하지 않는다.
대상은 여전히 실제 소유한 전체 이름이나 현재 선택한 카드여야 하며 stale revision·만료·
결과 불명·근거 철회는 기존 guard에서 거절한다. 추가 승인 창이나 background 범위 확대는 없다.
개인 ChatGPT의 새 도구 실행은 원래 현재 요청의 명시적 위임으로 읽기 업무/예약을 생성·제어하고 같은 제한된 답변을 이어받을 수 있다. 기존 Calendar 전용 실행은 소급 확대하지 않는다.

바로 앞에서 저장/제어한 실제 업무 영수증이 있으면 `그 업무 멈춰줘`처럼 지금 보낸 명확한
제어 요청으로 같은 target ID/revision을 이어 쓸 수 있다. 일반 인사·질문에 영수증만으로
제어를 실행하지 않는다. 별도로 선택한 카드는 우선하며, 이전 revision이 바뀌었거나 대상이
만료/철회됐으면 새 대상을 임의로 고르지 않는다. 영수증은 식별 근거이며 작업 권한은 현재
제어 요청에서 나온다.

## 예약 업무의 스킬 중단과 복구

예약 때 보였던 모든 스킬을 의존성으로 취급하지 않는다. 실제 회차에서 읽은 정확한
지침 pin만 원래 예약의 의존성으로 남는다. 비활성화와 읽기 사이에 경합한 실제 저장
호출도 그 pin만 복구 대상으로 남긴다. 해당 설치를 끄거나 삭제하면 관련 예약은
`needs_skill` 사유로 멈추고 미완료 회차는 은퇴한다. 다른 예약·다른 사용자는 영향을
받지 않는다. 기록된 사용량·도구 영수증과 원래 시간·호출 한도는 보존한다.

업데이트·이전판 전환 뒤에도 활성/이전 포인터에 정확히 남은 원래 pin은 사용할 수
있다. 새 버전으로 자동 치환하지 않으며 그 pin이 더 이상 남아 있지 않으면 멈춘다.
다시 활성화한 뒤에도 자동 재개하지 않는다. 원래 pin이 허용된 상태에서 **다음 회차부터
재개**를 직접 선택해야 하며 지난 회차나 은퇴한 실행은 다시 보내지 않는다. 새 회차의
발견 목록은 원래 profile과 현재 허용된 설치의 교집합이다. 단순히 광고되던 스킬을
삭제했다고 무관한 예약까지 멈추거나, 저장된 옛 목록으로 삭제한 지침을 다시 읽지 않는다.
복원한 예약의 기존 격리·명시적 재개 경계도 그대로다. private 실행 route는 여전히
미션에서 제외하며 별도 예약 실행 권한을 얻지 않는다.


## 연결된 Gmail·Calendar 읽기 위임

`매일 아침9시에 Gmail과 Calendar를 읽고 요약해 줘`처럼 **현재 요청의 업무 본문**에
Gmail/mail/email/메일 또는 Calendar/캘린더/일정을 명시하면 해당 영역의 읽기를 맡길 수 있다.
직접 일회/예약 양식도 같은 이름을 사용한다. 영역을 추가하려면 새 업무로 맡긴다. 현재
연결된 소유 계정의 정확한 connection epoch·OAuth client/app revision·Calendar primary ID를
원래 업무와 함께 고정하며, 이전에 저장한 업무에는 이 읽기 권한을 소급하지 않는다.
연결이 없거나 app에 묶이지 않은 옛 연결이면 `needs_connection`으로 안내하고, 요청한 영역을
빼고 보관 자료만 읽는 축소 업무를 저장하지 않는다. 연결 후 원래 전체 업무를 새로 맡긴다.

별도 로그인 세션이나 UserContext를 만들어내지 않는다. 기존 mission owner/account epoch,
원래 provider/model/effort, 실행 mode, 예약 parent와 시작된 typed read permit에서만 credential
carrier를 만든다. durable grant는 정상 로그아웃 후에도 유효하지만 계정 정지·세대 변경·임시
계정 만료·연결 철회에는 유효하지 않다. current_session 업무는 원래 실제 세션이 필요하며
새 로그인으로 이어 붙이지 않는다. 개인 ChatGPT 연결의 background 권한은 추가하지 않는다.

허용 도구는 Gmail search/read/thread 및 소유 기본 Calendar list/read다. Gmail message/thread ID는
**이번 회차**의 실제 완료된 읽기 근거에서 나와야 하고, Calendar는 이번 run의 opaque
observation_ref만 읽는다. 메일 검색은 최대5개, 본문4096bytes, thread 최근3개이며 Calendar는
최대31일 범위·페이지5개다. 일부 페이지는 전체 부재를 증명하지 않는다. 매 회차 새 기준 시각과
원래 Calendar 시간대를 제공하며 과거 회차의 결과·ID를 새 조회 영수증으로 사용하지 않는다.
발송·답장·초안 작성·Calendar 변경/작업 조회·브라우저·볼트·첨부·외부 쓰기는 허용하지 않는다.
결과는 private 업무 기록과 기존 상태 소식에만 남고, 자료/일반 모델 출력은 새 위임 권한이 아니다.

접수·IO 직전/직후·결과 저장에서 owner/epoch/원래 session mode/parent/provider/connection/app
pin을 검사한다. refresh도 원래 owner·connection·app 및 credential revision CAS로 저장하고
scope를 늘리지 않는다. 읽기 권한이 사라지면 결과·private checkpoint/observation/후보를 제거하며
최소 dispatch/accounting 영수증은 보존한다. 정지·취소도 연결 읽기의 private projection을 은퇴시키고,
이미 시작한 작업은 결과 불명으로 남겨 자동 재실행하지 않는다. 안정된 정지 업무를 원래 권한으로
재개하더라도 새 읽기만 사용할 수 있고 예산은 그대로다. 재연결은 옛 pin을 바꾸지 않으므로 새 업무가
필요하다. 보관했던 결과도 연결 철회 뒤 되살아나지 않는다.

기존 회차당 모델6회·도구12회·120초 누적 실행 한도와 최대 하루 유효기간을 유지한다. 승인 창을
추가하지 않는다. 합성 Store/Runtime 및 실제 loopback connector 검증은 실제 Google 계정 동의,
넓은 언어 이해 정확도, 실계정 정책이나 production 배포 검증을 뜻하지 않는다.

## 개인 ChatGPT로 맡기는 읽기 업무

설치 공용 API 모델 없이도 소유자가 선택한 개인 ChatGPT 연결로 기존 일회성·반복
읽기 업무를 맡길 수 있다. 정확한 연결 revision/model/effort의 text·도구 왕복 확인이
필요하다. 이 확인은 전송 기능 증명이며 background 실행 허용이 아니다. 실제 허용은
양식/API의 원래 업무 요청 또는 현재 대화에서 명시적으로 맡긴 요청을 같은 writer
트랜잭션에 저장한 owner mission grant에서 나온다. 매 실행 확인을 반복하지 않는다.

‘매 2분마다 0.1과 0.2를 더해서 확인해 줘’처럼 명시한 반복 업무도 새 개인 도구 대화에서
기존 해석·원문 인용·저장 영수증 경로를 사용한다. 선택한 업무의 정지/재개/취소도
현재 요청에서만 처리한다. 과거 Calendar 전용 실행이나 나중에 도구 확인을 통과한
기존 text 실행은 이 권한을 소급해서 얻지 않는다. 모델 출력·검색 자료·일반 대화 이력은
위임이 아니다. 개인 연결을 다른 가족이나 설치 공용 pool/default로 바꾸지 않는다.

원래 소유자·account epoch·binding revision·model/effort·읽기 profile과 하루/6회/12회
한도를 고정한다. 실제 모델 요청마다 기존 durable step/사용량 영수증과, 과거 복구로
계량이 불명확한 설치에서는 새 forward allowance를 먼저 기록한다. 유휴 예약 확인은
DB만 읽으며 모델을 호출하지 않는다. durable 위임은 정상 로그아웃 뒤에도 남지만
current-session 위임은 원래 세션이 끝나면 실행하지 않는다. 계정 세대·연결 철회·취소·
복원 격리와 이미 시작한 호출의 unknown/no-reentry 계약은 공용 모델 업무와 같다.

지원 범위는 기존 보관 자료·기억/지침 읽기·정확 계산·설정된 공개 HTTP와 명시해서
맡긴 개인 Gmail/기본 Calendar 읽기다. 메일/Calendar 쓰기·브라우저·볼트·media·Claude
background는 추가하지 않았다. 원래 요청에 필요한 연결이 사라지면 다른 계정이나
공용 모델로 우회하지 않는다. 개인 연결 token은 기존 sealing/refresh 전용 경로만 쓰며
모델·업무 결과·일반 도구 output에 복사하지 않는다. 합성 공식 protocol/Runtime 검증은
실계정 eligibility나 자연어 품질 평가를 대신하지 않는다.

영어 `every minute`·`every hour`처럼 정확한 단수 단위의 반복 인용문은 각각60초·3600초로
확인한다. 단위가 다른 제안이나 상대 지연으로의 재해석·모호한 시각은 허용하지 않는다.
숫자가 있는 기존 간격과 최소60초 조건도 그대로다.
