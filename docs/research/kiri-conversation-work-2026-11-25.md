# Kiri에서 대화 한 번으로 일을 맡기려면

**“지난 출장 때 몇 시에 출발하기로 했는지랑 챙길 것, 한 장으로 정리해서 저장해 줘.”** 이 부탁을 채팅 한 줄로 끝내는 일을 첫 개발 단위로 제안한다. Kiri가 이전 대화와 기억을 찾아 출처가 있는 준비표를 저장하고, 같은 대화에 열 수 있는 결과를 돌려준다. 사용자는 검색어를 다시 쓰거나, 도구를 고르거나, 보고서 버튼을 찾아갈 필요가 없다. 출장이 두 건이라 결정이 어려울 때만 어느 출장인지 묻는다.

2026-11-25 Linux에서 확인한 가장 큰 차이는 **표현이 달라지면 같은 일이 시작되지 않고, 앞에서 찾은 결과를 다음 말에서 가리킬 수 없다는 점**이다. 회원별 업무 저장과 보고서 열기는 이미 동작한다. 첫 개선은 기존 기능을 말 한마디로 이어 주는 것이다. 운영 Kiri, Linux에서 검증한 로컬 개편판, 표준 서버의 범위는 제품 상태 문서에서 관리한다. [현재 적용 범위](../status.md) · [회원별 실행 설계](../../openspec/changes/isolate-account-runtime/design.md)

이 문서의 현행판 대조는 스키마 92에서 수행했다. 이후 각 결함의 수정과 사용 사례의 수락 결과는 [구현 워크로그](../reviews/2026-11-25-member-work-from-chat.md)에 이어 기록했다.

## 실제 Muse 계정에서 맡긴 일

11월 25일 회원으로 로그인해 주 대화의 11월 17~24일 구간과 ‘활동 → 예약된 작업’을 직접 열었다. 화면에 올라온 메시지를 중복 제거한 결과 사용자 발화 76개, Muse 발화 186개였다. 예약 목록에는 5개가 있었다. 한 명의 사용 방식과 후속 지시를 본 표본이다. 아래 예시는 고유명사·주소·인증정보를 제거하고 새로 만든 합성 업무다. Muse가 대화에서 보고한 신청·구매와 외부 서비스의 최종 접수 여부는 독립적으로 확인하지 않았다.

| 사용 기록에서 관찰한 흐름 | 무수리에서 재현할 대표 부탁과 끝나는 지점 |
| --- | --- |
| 한 주제에서 장소·챕터·비용을 아주 짧게 이어 묻고 잘못 짚은 조건을 정정했다. 게임 공략에도 이런 대화가 이어졌다. | “이 미션의 차고가 어디야?” → “항구 쪽에 있어” → “그럼 비용은?” 대상과 현재 진행 단계를 이어받아, 출처가 있는 위치·비용으로 답한다. 독립 업무를 만들 이유가 없는 짧은 질문은 같은 대화에 남긴다. |
| 연구자에게 적용될 무료 이용·지원 자격을 찾고, 본인의 연구 관련 메일을 근거로 신청 내용을 작성해 진행해 달라고 했다. | “내 연구 메일을 보고 지원 가능한 크레딧을 찾아 신청 초안을 써 줘.” 공고의 대상·기간·비용과 읽을 수 있는 메일 근거를 대조하고, 근거 없는 지원 자격은 미확인으로 둔다. 준비한 문서와 실제 제출이 각각 확인 가능해야 한다. |
| 주문을 진행하면서 도착 기한을 덧붙이고 배송·결제 조건을 확인했다. 계정이나 본인 입력이 필요한 지점에서 브라우저를 넘겨 달라고 했다. | 합성 상품 2개 중 금요일까지 도착하는 옵션을 추려 총액·배송 조건을 보여 준다. 본인 입력은 같은 탭에서 회원에게 넘기고, 다시 맡기면 주문번호·상태를 조회한다. 샌드박스 상점에서만 결제 경계를 시험한다. |
| 메일·브라우저·계정 연결을 오가고, 연결이 바뀌었을 때 다른 메일이나 본인 인증으로 이어가기를 요청했다. | “다른 시험 계정으로 연결해서 아까 하던 것 계속해.” 현재 계정과 작업을 확인하고 이전 계정의 결과를 숨긴다. 회원이 직접 인증을 마치면 완료된 조회를 중복하지 않고 필요한 단계부터 재개한다. |
| 예약 화면에서 주기적인 서비스 점검, 캘린더 자동화, 정해진 시각의 아침 브리핑이 보였다. 대화가 없는 날에도 활동 기록이 있었다. | “서비스가 달라질 때만 알려 줘”, “아침에 오늘 일정과 중요한 메일만 알려 줘.” 정해진 대상·시간대·회차가 실제로 저장되고, 변화가 없으면 알림 0건, 변화가 있으면 원문이 열리는 알림 1건이어야 한다. |

출장 준비표는 계정 연결 없이 대화·연구·저장을 한 번에 확인할 첫 대조군이다. 실사용 판단에는 위의 **짧은 후속 질문, 메일 기반 지원 준비, 기한이 있는 구매와 본인 인계, 반복 점검과 브리핑**을 함께 사용한다.

## Linux에서 같은 일을 두 방식으로 부탁한 결과

제품 코드 `905a9a2`, 회원 스키마 92의 개편판을 Linux x86_64의 격리된 회원 서비스·HTTPS 게이트웨이·Chromium으로 실행했다. 출장 일정은 합성 대화에, 전자기기 표식과 회색 외투는 수동 기억에만 넣었다. 채팅에서 실제 전송 경로, 회원 SQLite의 전후 차이, 다시 연 결과를 확인했다. 모델을 부른 사례는 공식 Claude Sonnet 5.5의 `medium` 설정을 사용했다. [실행 관측값](../../audit/runs/kiri-conversation-routing-2026-11-25.json) · [회원 웹 검증 환경](../../deployment/kiri/linux-vm-smoke/member-web-fullstack.py) · [모델 사용 확인](../../audit/claude_cli.py)

| 회원이 한 일 | 관측한 결과 |
| --- | --- |
| 1. “지난 출장 대화에서 정해진 일정을 찾아주고, 내 기억에서 준비물도 찾아줘” | 업무 묶음 1개, 자식 업무 2개, 검색 실행 2개가 생겼다. 준비물 카드에 전자기기 표식과 외투가 보였다. |
| 2. “출장 때 언제 출발하기로 했는지 전에 나눈 얘기에서 확인하고, 챙길 건 내가 적어 둔 기억에서 꺼내 줘.” | 텍스트 답변이 저장됐다. 새 묶음·업무·검색 실행은 모두 0개였다. |
| 3. 같은 두 카드에서 “두 번째 건은 전자기기만” | 화면에 해당 검색을 찾지 못했다는 안내가 나왔다. 모델 호출과 추가 검색은 각각 0건이었다. |
| 4. “준비물은 전자기기만” | 준비물 업무의 실행만 1개 늘었다. 표식은 보였고 외투는 결과에서 빠졌다. |
| 5. “방금 찾은 전자기기 준비물의 확인 표식은 뭐야? 근거에 적힌 대로 답해 줘.” | 카드에 있던 합성 표식이 모델에 보낸 대화 문맥과 실제 답변 양쪽에서 빠졌다. |
| 6. “방금 정리한 준비물로 보고서 한 장 저장해 줘.” | 텍스트 전용 경로로 답변을 받았다. 저장된 보고서는 0개였다. |
| 7. 같은 준비물 카드의 ‘보고서 만들기’를 누른 뒤 새로고침 | 보고서 1개가 생겼다. 원래 검색 회차와 연결됐고 다시 열었을 때 표식이 보였다. |

1~5번은 같은 회원·대화에서 수행했다. 이어진 6번의 첫 시도는 시험기가 완료된 텍스트 응답을 확인하는 단계에서 멈췄다. 이 원인은 확정하지 못했다. 6~7번은 새 임시 회원에 같은 두 기억과 좁힌 준비물 카드를 만들고 한 쌍으로 다시 측정했다. 세 동작에서 업무 수행을 확인했고 네 동작에서 격차를 재현했다. 비교를 위해 고른 사례의 결과이며 전체 성공률을 추정할 표본은 아니다. 직전의 27개 업무 시나리오와 7개 Claude 대화는 당시 정의한 기능의 별도 수락 기록이다. [직전 워크로그](../reviews/2026-11-25-conversation-work.md)

재현할 때는 위 문장을 **메시지 입력창**으로 보내고, 업무 요청 `/personal/tasks/conversations/{thread}`, 후속 조작 `/control`, 일반 응답 `/threads/{thread}/text-preview` 중 실제 요청을 확인한다. 같은 회원의 `member_conversation_groups`, `member_conversation_tasks`, `member_conversation_runs`, `member_conversation_reports`를 조작 전후에 센다. 보고서는 `task_id`와 `run_id`를 함께 대조하고 브라우저에서 다시 연다. 모델 입력 검사는 허용한 합성 대화만 받는 시험 공급자로 수행했다. **실행과 저장의 주체는 회원 컨테이너의 Rust 서비스다.** 공용 엔진은 설치자가 정한 모델·추론 강도와 사용량을 관리한다. 모델은 행동과 대상을 제안한다. 회원 서비스는 로그인한 계정, 볼륨 세대, 원래 위임, 대상 버전, 실제 허용 도구를 대조해 실행한다. `request_id`로 접수를 먼저 저장하고 외부 호출은 SQLite 쓰기 트랜잭션 밖에서 수행한다. 결과는 같은 업무·회차·호출에 묶는다. 모델 장애나 재연결을 만나도 접수한 일과 이미 확인된 단계는 찾을 수 있어야 한다. ## 개발 순서와 각 단계의 끝

1. **출장 준비표를 한 문장으로 맡기고 받는다.** 이미 있는 기억·대화 검색과 회차 보고서로 시작한다. 회원 런타임에 현재 발화·보인 업무·가능한 작업을 해석하는 접수를 둔다. 취소·변경은 대상이 유일하면 바로 적용하고 두 후보가 실제로 남을 때만 이름을 제시한다. 두 자료를 합친 한 장은 읽은 회차와 출처에 연결해 저장한다. “옷은 빼 줘”에 같은 업무가 수정되고, “표식이 뭐였지?”에 실제 근거로 답하며, 새로고침 뒤 같은 결과가 열리면 이 단위를 닫는다. [현재 검색 보고서](../member-tasks.md) · [재사용할 비공개 문서 저장](../compound-reports.md)
2. **같은 부탁에 웹과 연결 자료를 쓸 수 있게 한다.** 첫 단계의 입력창과 결과 표시를 그대로 쓴다. 공개 웹은 기존 회원 브라우저로, 명시한 Google 자료는 해당 회원의 읽기 연결로 조회한다. 원문 범위, 조회 시점, 충돌·누락, 사람이 제어 중인지를 보존한다. 예로 “안내문과 내 준비표의 집합 시간이 달라?”에 두 출처의 시간을 보여 준다. 운영 Google 설정을 기다리는 동안 공개 웹과 합성 계정 조합은 독립적으로 검증할 수 있다. [회원 브라우저](../../deployment/kiri/browser.md) · [연결 범위](../../deployment/kiri/google.md)
3. **원하는 외부 결과 한 건을 끝낸다.** 메일은 “이 내용으로 회신할 초안 써 줘”에서 시작해 실제 초안, 최종 내용 확인, Google 발송 접수까지 이어 본다. 일정은 별도 작업으로 기본 개인 달력의 단일 일정 생성·이동부터 연결한다. 각각의 완료 조건은 공급자의 초안·메시지 ID 또는 이벤트 ID·버전과 재조회다. 받는 이의 배달·참석까지 추정하지 않는다. 실계정 조회·쓰기는 전용 시험 계정과 각 권한이 준비될 때 수락한다. [메일·일정 계약](../compound-actions.md) · [실행 전후 검사](../../crates/moosuri-store/src/missions/actions.rs)
4. **자주 하는 일을 다음번에 편하게 한다.** 완료한 업무의 근거를 이용해 “금요일에 바뀐 것만 알려줘”를 등록하고 변경·만료·해제까지 잇는다. 기억은 회원이 읽고 고치고 지울 수 있게 하며, 성공한 절차는 새 입력과 현재 권한으로 실행한다. 회원별 타이머와 표준 서버의 감시·기억·절차 구현을 필요한 순서로 옮긴다. [감시](../task-monitors.md) · [기억](../automatic-memory.md) · [절차 재사용](../learned-skills.md)

각 단위의 워크로그에는 **사용자의 부탁, 실제로 달라진 상태, 열 수 있는 결과, 막힌 이유와 재개 조건, Linux 검증, 운영 적용 상태**를 남긴다. 세부 단계는 펴서 볼 수 있다. 다음 개발과 이관 상태는 기존 Kiri 작업표에서 갱신한다. [전환 작업표](../../openspec/changes/isolate-account-runtime/tasks.md)

## 기능별 수락 시나리오

아래는 개발할 때 수행할 **10개 기능 × 4개 시나리오**다. 위의 현행판 관측 7건과 구분한다. 각 조작은 별도 언급이 없으면 회원의 일반 채팅에서 시작한다. 한 기능이 통과하면 그 결과를 워크로그에 연결하고 다음 기능으로 간다.

| 단계 · 기능 | 회원이 하는 일과 합격 조건 |
| --- | --- |
| 1 · 부탁 알아듣기 | ① 평소 말로 준비표를 맡긴다 → 입력 한 번으로 원래 턴에 접수된다. ② 같은 부탁을 다른 어순으로 말한다 → 같은 범위·완료 조건을 얻는다. ③ “어떤 일을 할 수 있어?”라고 묻는다 → 설명만 돌아오고 업무는 0개다. ④ “지난 출장 대화에서 일정을 찾아만 줘. 달력 등록은 하지 마” → 이전 대화를 읽고 쓰기 0건을 확인한다. |
| 1 · 여러 일에 이어 말하기 | ① 독립된 두 일을 맡겨 하나가 답을 기다린다 → 다른 하나는 끝난다. ② “두 번째 건만” 바꾼다 → 대상 회차만 늘어난다. ③ “그거 멈춰”에 가능한 대상이 둘이다 → 두 이름 중 골라 그 일만 멈춘다. ④ 창을 닫았다가 질문에 두 번 답한다 → 같은 업무가 한 번 이어지고 원래 요청과 이력이 열린다. |
| 1 · 앞서 찾은 근거로 답하기 | ① “방금 표식은?” → 기억에만 넣은 값과 출처가 맞는다. ② 이름이 같은 출장 두 건을 둔다 → 필요한 날짜만 물어 올바른 출처를 쓴다. ③ 두 기록의 출발 시간이 다르다 → 양쪽 시간·출처와 충돌을 보여 준다. ④ 한 근거를 수정·삭제하고 다시 묻는다 → 옛 발췌가 답변·다시 연 결과에서 사라진다. |
| 1 · 한 장으로 받기 | ① 일정과 준비물을 한 장으로 부탁한다 → 두 근거와 필수 항목을 담은 문서 하나를 채팅에서 연다. ② “옷은 빼 줘” → 같은 업무의 새 회차에서 수정된 문서를 열고 이전 회차를 찾을 수 있다. ③ 저장 성공 직후 접속을 끊고 재접속한다 → 같은 결과 하나가 열린다. ④ 저장을 실패시킨다 → 완료 링크가 생기지 않고 남은 단계가 표시된다. |
| 2 · 웹과 연결 자료 읽기 | ① 공개 안내문의 링크 한 단계 뒤에 있는 출발 시각을 묻는다 → 실제 읽은 원문과 값이 맞는다. ② 같은 페이지를 되풀이한다 → 실행이 중단되고 원래 대화에서 지시를 보탠다. ③ 사람이 브라우저를 넘겨받는다 → 입력 주체는 한 명이고 돌려준 탭에서 이어간다. ④ 지정한 내 문서를 읽는 도중 연결을 철회한다 → 결과 접근이 닫히고 다른 회원의 자료 호출은 0건이다. |
| 3 · 메일 초안과 발송 | ① 특정 메일에 답을 써 달라고 한다 → 올바른 원문·받는 이의 초안을 열고 발송은 0건이다. ② Gmail에 초안 저장을 부탁한다 → 공급자 초안 ID로 같은 초안을 다시 연다. ③ 최종 확인 중 받는 이나 본문을 고친다 → 새 내용을 확인한 뒤 그 버전만 접수된다. ④ 접수 뒤 응답을 잃는다 → 기존 원장을 조회하고 근거가 없으면 결과 불명을 표시하며 재발송은 0건이다. |
| 3 · 개인 일정 생성과 이동 | ① 시간대·길이가 정해진 일정을 맡긴다 → 실제 이벤트 하나를 다시 조회한다. ② 같은 이름의 일정 둘 중 하나를 옮겨 달라고 한다 → 날짜 하나를 물어 선택한 ID만 바뀐다. ③ 조회 뒤 달력에서 직접 수정한다 → 버전 충돌을 인지해 새 시각을 덮지 않는다. ④ 생성 직후 연결이 끊긴다 → 같은 ID로 확인해 중복 일정은 0개다. |
| 4 · 바뀔 때만 알림 받기 | ① 변동 감시를 부탁한다 → 대상·주기·종료 조건이 저장된다. ② 변화 없는 회차를 지난다 → 회원 알림 0건이다. ③ 같은 변경을 두 번 관측한다 → 근거가 열리는 알림 하나가 원래 업무에 남는다. ④ 해제·만료 뒤 원문이 바뀐다 → 새 실행·알림이 없다. |
| 4 · 기억 고치고 잊기 | ① “다음부터 출장에는 어댑터도 챙겨 줘” → 저장된 선호를 열고 다음 출장 준비표에서 확인한다. ② “이번 출장만 빼 줘” → 이번 결과만 바뀐다. ③ 선호를 고친 뒤 새 대화에서 묻는다 → 최신 값과 적용 범위가 맞는다. ④ 잊어 달라고 한 뒤 과거 업무를 다시 연다 → 파생된 옛 발췌와 다음 업무의 자동 적용이 사라진다. |
| 4 · 성공한 절차 다시 쓰기 | ① “다음 출장도 같은 식으로” → 새 날짜·목적지로 다시 읽는다. ② 이전 출처가 없어졌다 → 빠진 자료를 밝히고 지난 결과를 복사하지 않는다. ③ 지난번에만 허용한 외부 작업이 있다 → 현재 요청으로 허용된 범위만 실행한다. ④ 이번 검색이 실패한다 → 과거 성공과 현재 실패가 각 업무 이력에서 구분된다. |

**첫 수락의 사용성 기준**은 평범한 말로 보낸 한 번의 부탁, 필수 메뉴 이동 0회, 명확한 요청의 재입력 0회다. 결과를 열 때 같은 대화에서 한 번 누른다. 모호해서 물은 경우와 메일 최종 확인은 따로 센다. Linux의 데스크톱·모바일 폭에서 실제 조작 수, 접수까지 걸린 시간, 결과가 준비된 시간, 기다리는 동안 다른 대화를 할 수 있는지를 기록한다. 이후 대표 업무는 개발자가 보지 않은 바꿔 말하기·다른 자료로 시험하고, 같은 세계의 반복 성공은 별도 집계한다. 기존 출시 목표인 지시·대상·필수 조건 정확도 95% 이상, 불필요한 재확인 5% 이하, 대표 실행 가능 업무의 끝까지 성공 90% 이상은 그대로 평가한다. 이번 사례 실험으로 이 수치를 달성했다고 판정할 수 없다.
