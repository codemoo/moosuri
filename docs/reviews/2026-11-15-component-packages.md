# Separate native component package delivery — bounded acceptance

2026-11-15. Base:cb25283. The implemented package delivery is independently reviewed and Linux-validated below.
This is not an official distribution or physical-device acceptance.

Implemented `installation component manifest|verify|download` for separately signed
`credential-broker` and `vault-service` native packages. Exact component, explicit
expected target, SemVer, sequence, fixed filename and digest are purpose-tagged signed
metadata. Local verification refuses unknown/unbound files. Header/table/segment bounds
and entry points reject malformed/truncated ELF and thin Mach-O containers without
execution. Component/version/full ABI remain signed packager claims, as does fresh
source/compiler/SBOM evidence generated by `xtask component-provenance`.

Component HTTPS uses the existing signing pin, bounded ordinary TLS/no-redirect transport,
private owned nonrecursive cleanup and atomic no-replace publication. Final version,
component and target URL segments must agree. Existing assistant manifest/provenance
projection and install/update semantics remain separate; shared transport factoring is
additive. No protocol/adapter/dependency/CI/service/credential changes were made.
No delivery step executes downloaded code, pairs devices or deploys a vault.

Implementation-lane checks: direct installed stable rustfmt, `git diff --check`, Python AST parsing of the synthetic TLS handler and new document link existence.
No Cargo product build/test was run in this lane. Root owns the joined Linux Cargo lane,
real built artifact/asset acceptance and independent boundary review.

Root commands, using its existing toolchain/Cargo environment and embedded web assets:

```sh
cargo test --locked -p xtask component -- --nocapture
cargo test --locked -p xtask release::tests -- --nocapture
cargo test --locked -p moosuri --test component_packages -- --nocapture
cargo test --locked -p moosuri --bin moosuri component -- --nocapture
cargo test --locked -p moosuri --test signed_download -- --nocapture
cargo test --locked -p moosuri --test local_bundle -- --nocapture
```

The TLS test fixtures need Python3 stdlib SSL and OpenSSL on PATH. They create only
synthetic local certificates/signing keys and use the ordinary private CA option.
Normal default TLS distrust is exercised; there is no insecure HTTP/TLS test bypass.
Synthetic tests cover both component choices, five-file evidence-bearing and three-file
packages, signed component/target/purpose/version/path confusion, invalid signatures,
missing/tampered/partial/oversized/redirected binary, provenance tamper/inventory missing,
existing destinations, unknown local files, a fully signed truncated container and a synthetic native executable whose filesystem witness must never appear.
Pure contract tests cover machine identity, bounded ELF/Mach-O tables, SemVer and path
refusal. Xtask tests bind fresh inventory to both component identities and reject evidence
mutation without executing artifact bytes.

For actual prebuilt binaries, first build the vault React/WASM with the existing documented
build flow, then build both native components on the joined Linux target:

```sh
cargo build --locked -p moosuri-credential-broker -p moosuri-vault-service
MOOSURI_COMPONENT_TEST_TARGET=x86_64-unknown-linux-gnu \
MOOSURI_COMPONENT_TEST_BROKER=/absolute/joined-target/debug/moosuri-credential-broker \
MOOSURI_COMPONENT_TEST_VAULT=/absolute/joined-target/debug/moosuri-vault-service \
cargo test --locked -p moosuri --test component_packages \
  component_packages_real_prebuilt_broker_and_vault_signed_https_delivery \
  -- --ignored --nocapture
```

Adjust paths/target for the actual root lane; do not use another task's live target.
This opt-in fixture signs, downloads over normal loopback TLS, verifies and compares
actual bytes for each prebuilt executable. It does not execute/pair/start them or prove
vault assets/state compatibility. Root should separately record actual broker `--help`
and vault shell/embedded assets smoke evidence from its established synthetic runtime
fixtures before advertising built packages. Cross/native ARM/macOS execution, physical
device pairing and official signed artifact publication remain separate gates.

Recipient download→verify→explicit operator-run commands, trust and upgrade limits are
in [component packages](../component-packages.md). There is no component state migration,
service installer, antirollback store, rollback or automatic uninstall. User choices of
component and host remain explicit. Parent integration should update README/status and
native-companion/vault build-only wording once joined results and review are accepted.

## Root integration acceptance

All15 frozen file hashes matched before integration. Independent read-only review
accepted signature/purpose/component/target bindings, strict provenance separation,
no-execution container validation and unchanged assistant download protections.
The offline Linux x86_64 capsule passed component/provenance contract checks,
actual HTTPS positive and failure delivery cases, the no-execution witness,
existing assistant signed-download/local-bundle regressions and native builds of
the assistant, vault service and credential companion. The opt-in actual-binary
fixture signed, downloaded and byte-compared both real compiled components.

Warnings-denied all-target Clippy initially required an equivalent unsigned
sequence predicate simplification. The affected shared component tests, final
Clippy and assistant build then passed; unrelated successful behavior cases were
not repeated. Native startup additionally verified the companion CLI and vault
public shell, unauthenticated private-state rejection and exact served JS/CSS/WASM
bytes against the packaged vault assets. An initial smoke assertion expected200
for the documented204 liveness route; only that fixture was corrected.

All execution used synthetic data and isolated network-disabled containers with
loopback fixture HTTPS. No production services, account connections, official
signing keys, GitHub release assets or CI were changed. This proves the explicit
package path on Linux x86_64, not real-device pairing, separate-UID deployment,
mobile behavior, native ARM/macOS execution or full P10 release readiness.
