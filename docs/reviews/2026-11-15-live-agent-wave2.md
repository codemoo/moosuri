# 실모델 개발 평가 2차 — 2026-11-15

공개 기준 `9958af1`을 새로운 합성 세계8개에서 평가했다. 입력과 별도 판정 기준을 실행
전에 독립 작성·고정했으며, 실제 도구 기록과 계정별 저장 상태를 기준으로 판정했다.
최초 실패를 후속 수정 결과로 덮어쓰지 않는다. 이8세계×1회는32세계×3회 pilot,
독립 출시 holdout, 운영 provider 수락이나 이전 비서와의 우열 비교가 아니다.
수정 후에는 같은22개 요청을 새 DB에서 한 번씩 모두 재실행했고 독립 판정에서
22개 모두 통과했다. 수정에 사용한 사례의 개발 회귀 결과이며 새 holdout 점수는 아니다.

## 발견한 원인과 후속 수정

1. 문서 분류기의 `no_command`가 공유 호출 수를 늘리자, 업무 분류기가 이를 자기의
   이전 실행으로 오인했다. schema58에 내용 없는 분류기별 단계·시도·영수증·실행
   identity를 저장하고, 완료한 같은 실행의 문서 `no_command`만 다음 분류에 연결했다.
   전체 호출 한도는 유지하며 임의 호출·불명 결과·오래된 이력으로 실행 권한을 만들지 않는다.
2. 소유자를 명시한 기억 정정에서 대상 문구의 `내`가 빠진 것으로 재구성된다.
   정확한 제안 원문은 완료 시 삭제되므로 저장된 길이·현재 요청·두 후보로 추론한
   내용이며 직접 보존한 인용은 아니다. 모호한 대상을 바꾸지 않는 Store 동작은 유지하고
   현재 대상의 소유 표현을 보존하도록 분류 지침을 구체화했다.
3. 별도 예약 학습 시험에서 정확한 도구 결과 `38.6`을 최종 답변이 `38.60`으로 표시하면
   학습 근거가 되지 않았다. 부동소수점 없이 유한 소수 문자열을 정규화해 같은 값을
   인정한다. 실제 계산 기록·서로 다른 두 입력·원문/계정 경계는 유지한다. 독립 검토에서
   발견한 Markdown 뒤의 부호/숫자 숨김도 막았다.

기억 정정은 원래 기억 identity의 revision1→2와 실제 변경 영수증으로 확인했다.
다른 사람·다른 계정의 기억은 보존됐고 새 대화에서 변경한 값을 회상했다. 모호한
망각에는 변경 없이 확인을 요청하고, 명시한 대상만 payload/version/timeline/FTS에서
삭제했다. 내용 없는 tombstone은 남는다. 이후 새 대화에서 삭제한 값은 모른다고
답하고 관련 없는 기억과 별도 계정의 값은 계속 조회했다.

앞서 막힌4개 자료 요청은 모두 실제 읽기와 계산을 수행했다. 전시 수용 인원 비교는
현재 원문 전체를 읽고155분, 조건을 바꾼 후210분을 계산했다. 같은 대화에서 이미
읽은 현재 revision의 근거를 후속 답변이 재사용할 수 있다는 기존 기준을 실행 전에
명확히 했다. 매 턴 중복 읽기를 요구하지 않는다. 최초 세계는 전체 읽기가 한 번도
없어 원래 엄격 판정 실패를 유지한다. 원문에 삽입한 기억 변경 지시는 실행되지 않았다.
용량 계산의 후속 정정은24개 조건을 유지하며207mL→183.6mL로 바뀌었고, 원문에
없는 보존 기간은 추측하지 않았다.

두 학습 세계 모두 서로 다른 실제 A/B 근거2개로 사용 가능해진 뒤 새C에서 해당
학습 절차와 자식 도구를 실제 호출했다. 원문 계산C는 새 유일한 자료의 현재 revision을
다시 읽어73.65를 계산했고, C재사용을 세 번째 학습 근거로 세지 않았다. 원문14개는
revision/내용이 그대로였으며 관측한 자료 identity는 모두 요청 계정 소유였다.

정확 계산 미션은 실제 결과468.3을 검증해 `achieved`, 습도 판단 미션은 현재/이전
근거를 구분하고 사람 검토를 남겨 `partial`이었다. 후자를 완료로 과장하지 않은 것이
사전 기준에 맞는 통과다. 다만 로그아웃 뒤 수행 가능 여부에 불필요한 단서를 붙인
답변은 품질 개선 항목으로 남긴다. durable 저장을 확인했지만 이 두 미션에서 실제
로그아웃·강제 종료·재시작을 실행한 것은 아니다.

## 별도 숫자 학습·예약 후속 시험

최초 별도 시험은 두 계산 답변이 맞아도 금액 표기 때문에 학습 근거0개로 끝났다.
수정 바이너리에서는 같은 두 요청의 서로 다른 실제 계산이 학습 근거2개가 됐다.
이를 앞선8세계의 성공 수에 더하지 않았다.

새120초 간격의 합성 예약에서 다음 순서를 실제 시각으로 확인했고 독립 검토했다.

- 학습한 절차를 실제 호출해 정확한 계산 결과로 완료했다. 부모·자식 도구 기록과
  미션의 인용이 같은 실행을 가리켰고 재사용이 세 번째 학습 근거로 추가되지 않았다.
- 그 스킬을 끄자 사용 이력이 있는 예약이 `needs_skill`로 정지했다. 다음 실제 예정
  시각을 지나도 회차가 추가되지 않았다. 관련 없는 예약의 활성 상태도 API로 관측했다.
- 스킬을 다시 켠 뒤에도 정지를 유지했다. 명시적 재개 후 반환된 다음 시각·예약 버전에

## 통합 중 발견한 추가 결함과 검증

실제 Calendar 실행에서 기존 계획 테이블의 `CHECK(step=1)`이 다음 분류 단계의
결정을 거부했다. schema58에서 기존 row/키/외래키를 보존하며 기존1~6호출 범위를
받도록 테이블을 재구성했다. 별도 sealed restore 경로에도 schema58을 등록했다.
처음 독립 소스 검토가 놓친 두 경로는 실제 Runtime/복원 검사로 발견했고 수정 후
해당 차이와 이전 행 보존을 다시 독립 검토했다.

Calendar의 기존 후속 대화 검사는 처음15개 중11통과·4실패였다. 이 중3개는 현재
오류명·지원되는 연결 읽기·옛 schema로 낮춘 합성 DB의 잔여물에 관한 낡은 기대여서
현재 계약에 맞췄다. 나머지1개는 실제 제품 결함이었다. `10:00`으로 끝나는 원래
요청과 `45 minutes` 답변을 붙이면 답변 숫자가 이전 시각의 잘못된 접미사로 읽혔다.
검증된 같은 필드의 이전 인용만 인증한 이전 메시지에서 확인하고, 새 인용은 현재
답변 안에서만 검증하도록 고쳤다. 메시지 내부 개행·잘못된 시각·원래 필드 불변 규칙은
유지한다. 실제45분 Create의 시작/종료와, 과거 본문에서 숫자를 빌리는 잘못된 현재
답변의 거부를 확인했고 독립 검토했다.

Linux는 source hash를 확인한 별도 rootless container에서 네트워크 없이 검사했다.
관련 검사만 실행했으며 서로 겹치는 아래 숫자를 전체 고유 검사 수로 합산하지 않는다.
