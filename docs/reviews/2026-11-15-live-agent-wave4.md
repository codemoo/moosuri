# 새 합성 업무의 실모델 개발 평가 4차

기준 `fe3248c`에서 독립 작성한9세계·15요청을 먼저 고정했다. 작성자는 공개 기능 계약만
읽고 구현·옛 시험·이전 실행 결과를 보지 않았다. 기억 정정·모호한 대상·인용문·망각,
근거 계산·충돌한 자료·여러 원문 비교 보고서, 두 실제 결과 채택 후 새 입력 재사용,
수신인 보완 후 같은 로컬 초안 업무 재개를 포함한다.

모델은 `gpt-6.1-terra/high`다. 세계마다 새 SQLite와 합성 소유자/다른 계정을 사용한다.
정답은 별도 판정 파일에만 있으며 모델에는 사용자 요청과 실제 도구 결과만 전달한다.
연결은 기존 공식 로컬 로그인의 임시 이력 재입력 경로이며 운영 구독 연결의 수락이나
운영 응답 지연을 뜻하지 않는다. 연결 전체240호출·개별24초와 기존 앱 예산을 유지했다.

- 입력 SHA256: `70af9e23706faebc9d5179ab60471f3d5d8d66c54214d960944a074230cd5f55`.
- 판정 기준 SHA256: `ccf49c45a8a27219a1689f10fb283de4988972cb2e12c773983a5ce79460e075`.

## 최초 실행

15개 중13개를 실제 실행했다. 전체 계획 기준 엄격 통과는9/15요청·5/9세계다.
지원 전제를 충족한 사례만 따로 보면9/11요청·5/7세계이며 전체 분모를 대체하지 않는다.
중앙값15.233초와95백분위35.213초는 실패를 포함한13개 요청의 관측 시간이다.
임시 연결의 프로세스·이력 재입력 시간도 포함하므로 제품 최초 표시 시간이나 속도 개선율로
해석하지 않는다. 연결 전체72회에는 setup probe가 포함돼 업무 호출 수와 다르다.

- 기억 정정의 요일이 예약 분류를 먼저 거쳐 실행 오류·빈 답변으로 끝났다. 저장 사실은 바뀌지 않았다.
- 충돌 보고서는 의미상 정확했지만 `출처를 나누어`의 부분 문자열 때문에 계산이 필수로 표시돼 실제 문서를 저장하지 못했다.
- 학습A는 실제 원문·계산·보고서를 독립 판정 후 채택했다. B의 수량5가 다른 입력0.65에도
  부분 문자열로 나타나 기존 원문 인용 유일성 계약을 위반했다. **사례 작성의 전제 오류**로
  기록하며 기존 제품 계약 위반으로 채점하지 않는다. B는 채택하지 않았고 C의 두 proof
  전제도 충족되지 않았다. 정답·입력·실패 이력을 바꾸지 않는다.
- 수신인 보완 세계2요청은 합성 Gmail 연결 준비 전이어서 최초 실행에서는 미실행이다.

## 구현 보완

명시한 기억 변경 표현을 기존 기억 분류기로 바로 보내며, 실제 변경 권한과 대상 확인은
Store가 계속 검사한다. 자료를 나누어 표시하라는 표현은 나눗셈 요구로 취급하지 않는다.
숫자 인용은 완전한 수치 토큰만 센다. 수량5와 수수료0.65는 함께 쓸 수 있지만 독립된5가
두 번 있거나 부호/수치 일부·겹친 범위·모호한 원문이면 거절한다. 이 마지막 변경은 기존
계약의 사용성을 확장한 것이며 최초 저자 전제 오류를 소급해 지우지 않는다.

독립 소스 검토에서 인용된 기억 표현이 실제 예약을 막는 회귀와, 진짜 나눗셈의 계산
요구가 빠지는 회귀를 발견했다. 기억은 인용되지 않은 완결 명령절만 앞서 처리하고,
명시된 수량/숫자로 나누는 요구는 계산 영수증을 요구하도록 고쳤다. 실제 Runtime에서
인용문을 검색하는 반복 업무 생성과 모호한 기억의 미변경을 확인했다. 두 P2의 수정도
독립 재검토를 통과했다.

## 수정 후 같은 요청 재실행

처음 고정한 입력·oracle 그대로 새 DB에서13개를 실행했다. 전체 계획 대비11/15요청·
7/9세계가 통과했고 W08 두 요청은 아직 별도 fixture 준비 중이었다. 실제 실행13개 기준
중앙값16.200초,95백분위29.543초이며 bridge 호출69회에는 setup probe가 포함된다.
기억 정정/모호함과 충돌 보고서가 통과했다. 이 관측으로 일반 응답 속도가 개선됐다고
주장하지 않는다. 단, 직접 기억 명령의 불필요한 일정 분류 호출 제거는 계수한 실제
Runtime에서 확인했다. unknown token usage는 추정값으로 채우지 않는다.

W07-B에서는 모델이 현재 요청에 두 번 나타나는 짧은 source query를 골라 근거 계산이
거절됐다. 일반 계산·정확한 보고서는 만들었지만 source-bound proof가 없어 채택하지
않았고, C도 두 proof 전제를 충족하지 못했다. 기존 성공 proof를 재사용해 통과시키지 않았다.

## 남은 사례의 최종 검증

도구 설명에 전체 원문 제목을 이용해 현재 입력의 유일한 검색어를 선택하도록 명확히
적고 완전한 숫자 토큰 계약을 맞췄다. 설명을 늘리는 과정에서 기존1024-byte 제한을
넘긴 회귀가 실제 preflight에서 context_limit으로 나타났다. 제한을 바꾸지 않고905byte로
줄였고 shared/personal combined-tool encode/continuation을 실제 검사했다.
동일 W07의 새 실행은 A1개 통과·B실패·C전제 미충족,1/3요청·0/1세계다.
B는 짧은 query를 고친 뒤에도 이전 search receipt를 가리켜 다시 거절됐고 예산을
소진했다. C는 없는 개인 절차를 묻는 context 대기로 끝났다. 실제 proof1개·learned use0회로,
학습 재사용 성공으로 셀 수 없다. A22.315초/B31.593초/C질문까지19.593초다.

별도 설정 실패도 보존했다. 초기 샌드박스가 공식 실행기의 상태 DB를 막은 시도는
업무0개였고, 새 임시 binary에 웹 assets가 빠진 시도도 업무0개다. 설명 길이 회귀는
계획 이후3개가 실제 실패했다. 새 blind/holdout 성적으로 합치거나 최초 실패를 지우지 않는다.

## 메일 초안과 수신인 이어하기

실제 Store OAuth seed·Router·Runtime를 사용하는 private test host로 W08을 보완했다.
Google만 loopback 합성 provider로 주입하고 non-GET을 거절한다. 정상 런타임의 판단/
권한/원문 조회/초안 저장을 바꾸지 않고, 모델에는 정답을 주지 않는다. 별도 startup fixture
소스와 binary로 실행했으므로 원본 baseline binary 또는 실제 Google 계정 수락과 구분한다.

첫 W08에서 모델은 올바른 수신인 질문 JSON을 냈지만 `발송은 하지 마`가 초안 action
contract까지 막았다. `초안을 준비하는 일`의 명시적 위임도 보완하고, 발송 금지와 별도의
초안 작성 금지를 구분했다. Store에서 같은 업무의 수신인 대기→답변→중복 답변→초안1개,
실제 dispatch0을 확인했고 독립 검토도 통과했다. 실제 발송은 여전히 매번 최종 승인이 필요하다.
후속 fixture 실행의 setup tool-probe가 완료 답 대신 도구를 반복한 실패는 업무0개로 별도 남겼다.

최종 W08에서는 같은 mission ID의 수신인 질문과 답변을 이어 실제 원문에 근거한
초안1개를 저장했다. 수신인·제목이 맞고 현재 action은 pending_approval이며 Google
호출/쓰기/발송은0회다. 질문까지7.296초, 답변 후 초안까지18.034초였다.
독립 기능 판정은2/2다. 다만 동결 oracle에 작성자가 넣은 불필요한 “질문 전에 원문을
먼저 읽어야 한다” 조건까지 기계적으로 적용하면1/2다. 작성자는 공개 기능 계약의
필수 조건이 아니라고 판정했으나 **oracle을 수정하지 않았고 두 판정을 함께 남긴다**.
이 두 요청을 다른 binary의13개 재검증과 합쳐15/15나 단일 최종 점수로 표현하지 않는다.
