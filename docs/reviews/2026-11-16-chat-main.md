# Main-chat action and deletion recovery

Frontend-only worker from `7fa6b73`, using synthetic accounts, conversations, HTTP responses and SSE streams. No native Cargo, production/private data, real provider calls or publication. Parent integration owns independent review and real-browser smoke.

## Consequential defects reproduced

1. Retry of the latest failed turn left the next-message send button enabled while its admission was unresolved; the reverse ordering left Retry enabled while a new question was awaiting admission. Both focused UI observations failed before the fix. A shared same-thread mutation fence now checks handlers as well as controls, preserving the next draft and immutable uncertain request.
2. A later SSE turn left a previous failed turn's old can_retry control available. Its focused UI observation failed before the fix. Retry now requires the actual current latest eligible turn and no active run, in addition to server authority.
3. A canonical higher retry attempt could already be streaming while its lost HTTP receipt still showed Processing and disabled cancellation. The focused observation failed before the fix. Canonical history/SSE now settles the redundant HTTP wait on the exact target transition. A streamed higher attempt permits immediate explicit Cancel with that attempt's expected_attempt. Canonical settled cancellation similarly permits the next message. Immutable action ownership prevents discarded responses/cleanup from affecting a newer action; no write is replayed automatically.
4. A silent DELETE left a blocking dialog with no usable close/cancel controls forever. The focused UI observation failed before the fix. DELETE now has one 30-second complete-response bound followed, only for an unknown receipt, by one authenticated inventory GET with its existing 30-second bound. Absence confirms removal. Presence or an unavailable inventory keeps the result unknown and restores usable dialog controls. A fully silent pair is bounded to 60 seconds while browser timers run; no automatic DELETE replay occurs.
5. Deletion success filtered its captured thread array, dropping conversations refreshed while the response was waiting, and an older in-flight inventory could restore removed rows. A controlled test against the original base App.tsx reproduced the lost refreshed conversation. Confirmation now filters only the target from latest state, preserves current selection/new conversations and aborts the older inventory transport. Its late body is discarded.

Dead-slot draft/pending callbacks also refuse to repopulate memory after confirmed removal. The background-admission/late 409 test remains a continuity/privacy regression observation, not a claim of a newly observed persisted-text leak: the previous persister already filtered removed slots. Existing independent account/session request fences remain controlling.

## Audit scope and remaining boundaries

Source review covered send/new-thread migration, selected/running-thread switch and deletion, run attempt/state ordering, SSE reset/reconnect/snapshot epochs, older-page fencing, attachment selection identity, persisted draft carriers and account/tab transport lifetimes. The retry server route returns its transaction snapshot before runtime wake; this review did not invent a cursorless retry-delta race without a source-supported sequence. Browser-suspension deadlines, real mobile keyboards, live model quality, provider/network latency and backend/store execution are not established by these tests. No API, model/effort, external effect or final mail-approval contract changed.

## Independent deletion-owner follow-up

Parent review found that authoritative SSE not_found already removed the target and closed its dialog, but its still-pending DELETE kept the global deletion controls disabled until the receipt deadline. The new focused regression failed before the follow-up because Delete Other conversation stayed disabled.

Deletion now owns an immutable target/controller identity. Authoritative target absence immediately releases and aborts that matching DELETE or inventory wait. Discarded response/catch/finally paths cannot clear the busy state or close the dialog of a newer deletion. The regression observes one held DELETE, streamed target absence, a second explicitly requested deletion, disposal of the first late body and preservation of the second busy dialog until its own receipt.

Seven focused deletion tests across Chat.test.tsx/App.test.tsx passed with 72 unrelated tests skipped, app/worker TypeScript checks passed, strict named OpenSpec validation and diff check passed. The earlier broad-suite/build evidence above belongs to the first frozen commit; the follow-up deliberately reran only changed deletion boundaries and TypeScript checks.
