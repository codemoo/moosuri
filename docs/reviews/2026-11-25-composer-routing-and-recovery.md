# 회원 입력창의 업무 판별과 전송 복구

Linux Chromium의 회원 입력창에 새 시나리오 32개를 적용했다. 기준 빌드 `f89fa3f`는 8개를 통과했고, 수정한 빌드는 32개 모두 통과했다. 같은 실행 파일에서 기존 실사용 시나리오 25개도 다시 통과했다. 57개 사례에서 보낸 메시지 93건에 대해 Claude Sonnet 5.5(`medium`)의 업무 해석 58회와 대화 답변 51회를 확인했다. 전체 목록과 빌드 SHA-256은 실행 집계에 있다. | 사례 | 회원의 요청 | 기준 빌드 | 수정 후 확인한 결과 |
| --- | --- | --- | --- |
| INT-01 | 10시 10분과 25분에 도착하는 버스를 비교한다. | 실패 | 일반 대화에서 15분 차이라고 답했다. 구매 업무가 생기지 않았다. |
| INT-02 | 메일 답장 초안의 인사와 맺음말을 어떻게 쓰는지 묻는다. | 실패 | 회원 화면과 SQLite에 같은 설명이 남았다. Gmail 작업은 0건이었다. |
| INT-03 | 캘린더에서 회의를 등록하는 방법을 묻는다. | 실패 | 제목과 시간 입력에 관한 대화 답변을 확인했다. |
| INT-04 | 인용한 메일·회의 지시의 뜻을 묻는다. | 통과 | 답변 1건이 저장됐고 메일·캘린더 쓰기는 0건이었다. |
| INT-05 | 참고 가격 8만 원, 예산 5만 원 이하로 판매처를 비교한다. | 실패 | 저장된 상한은 50,000원이었다. 새로고침 후에도 비교와 연결된 업무가 각각 1건이었다. |
| INT-06 | 내일 오후 3시, 30분짜리 회의를 등록해 달라고 한다. | 통과 | 캘린더 연결 상태를 조회했고 외부 일정 쓰기는 0건이었다. |
| INT-07 | 제품 구매와 배송을 마쳤다고 말하고 끝낸 두 가지를 묻는다. | 실패 | 일반 대화로 답하고 구매 업무가 생기지 않았다. |
| INT-08 | 지난 참고 가격만 알려주고 새 비교를 맡긴다. | 실패 | 비교 업무를 만들고 예산 상한은 비워 두었다. |

입력창의 전송 가능 여부와 제출 처리가 같은 업무 판별 함수를 사용한다. 구매·메일·일정 표현의 해석은 화면 컴포넌트에서 옮겼고, 직접 업무로 처리할 근거가 부족하면 기존 회원 해석 경로로 보낸다. [업무 판별](../../web/src/member-work-intent.ts) · [시나리오](../../deployment/kiri/linux-vm-smoke/member_live_composer.py)

## 감시 주기와 기간

| 사례 | 회원의 요청 | 기준 빌드 | 수정 후 확인한 결과 |
| --- | --- | --- | --- |
| TIME-01 | 두 시간마다 교통 공지를 확인해 달라고 한다. | 실패 | 지원하는 간격을 표시하고 원문을 편집할 수 있었다. 감시 건수는 그대로였다. |
| TIME-02 | 점검 일정이 바뀌면 반 시간마다 이틀 동안 알려 달라고 한다. | 실패 | 목록과 DB의 값이 1,800초·2일로 일치했다. |
| TIME-03 | ‘10분마다 점검 90일 동안’이라는 문구를 매시간 감시한다. | 통과 | 인용문 전체가 검색어로 남았고 실제 조건은 1시간·기본 7일이었다. |
| TIME-04 | 공개 페이지를 반 시간마다 이틀간 감시하고 나중에 멈춘다. | 실패 | 새로고침 뒤 같은 감시에 30분·2일이 표시됐다. 중지 후 같은 ID의 상태가 바뀌었다. |
| TIME-05 | 서로 다른 주기나 기간을 한 요청에 함께 쓴다. | 실패 | 개인·공개 감시와 하루 한 번인 연결 브리핑에서 충돌을 알렸다. 원문은 입력창에 남았다. |
| TIME-06 | 매주 요청이 거절된 뒤 매일 사흘로 고친다. | 실패 | 86,400초·3일인 감시 한 건만 추가됐다. |
| TIME-07 | 당직 교대 기억을 1시간 30분마다 확인해 달라고 한다. | 실패 | 90분이라는 전체 간격을 읽고 지원하는 주기를 안내했다. 입력은 남았고 감시 건수는 그대로였다. |
| TIME-08 | 공개 페이지를 30분마다 2시간 동안 확인해 달라고 한다. | 실패 | 일 단위로 지정할 수 있는 기간을 안내했다. 회원 DB에 새 감시가 생기지 않았다. |
| TIME-09 | 출고 공지를 매 30분 간격으로 48시간 동안 확인해 달라고 한다. | 실패 | 회원 화면에 30분·2일이 표시됐고 같은 요청 ID의 DB 값은 1,800초·2일이었다. |
| TIME-10 | 공개 페이지를 하루 두 번 확인해 달라고 하고, 개인 감시에는 12월 25일까지를 지정한다. 이어서 하루 한 번 일주일로 고친다. | 실패 | 처음 두 요청은 조건을 안내했고 입력창에 원문이 남았다. 수정한 요청에서만 하루 간격·7일 감시가 생겼다. |

## 응답 유실과 수동 복구

| 사례 | 장애를 넣은 지점 | 기준 빌드 | 수정 후 확인한 결과 |
| --- | --- | --- | --- |
| ACK-01 | 감시가 저장된 뒤 응답과 대화 기록 조회를 끊는다. | 통과 | 회원이 재확인하자 같은 요청 ID와 본문으로 응답했다. 감시 1건, 원래 대화 기록 1건이었다. |
| ACK-02 | 답변 요청을 보류한 동안 다음 글을 쓰고 첫 요청을 거절한다. | 통과 | 새로고침 후 다음 글이 남았다. 이전 메시지를 다시 보내자 원래 ID로 실제 답변 하나가 저장됐다. |
| ACK-03 | ‘일반 메시지로 보내기’를 선택한 뒤 서버 도착 전에 연결을 끊는다. | 실패 | 새로고침 후 같은 ID로 일반 메시지를 보냈다. 업무 재해석 0회, 실제 답변 1회였다. |
| ACK-04 | 감시 A 중지 응답을 잃고 두 번째 탭에서 같은 이름의 B를 만든다. | 실패 | 재시도는 A의 ID·버전·요청 ID를 사용했다. SQLite에서 A는 중지, B는 진행 중이었다. |
| ACK-05 | 감시 중지 요청에 HTTP 409 상태 충돌을 돌려준다. | 실패 | 원문과 최신 목록으로 돌아왔다. 목록에서 직접 멈추자 해당 감시가 종료됐다. |

재시도에 필요한 전송 경로, 감시 생성 조건, 중지 대상 ID와 버전을 회원·세션 범위의 기존 탭 저장 형식에 담았다. 중지 요청을 보내기 전에 대상을 기록한다. 구버전 데이터에 중지 대상이 없으면 원문과 현재 목록을 보여준다. [탭 복구](../../web/src/chat-drafts.ts) · [감시 제출](../../web/src/member-monitor-command.ts) · [시나리오](../../deployment/kiri/linux-vm-smoke/member_live_ack.py)

## 실행 환경과 증거

회원 화면은 격리된 HTTPS 게이트웨이, 실제 Rust 회원 서비스와 임시 SQLite 볼륨을 사용했다. ACK와 TAB의 지정 지점에서만 지연·단절·거절을 주입했다. 캘린더와 메일은 연결 또는 최종 확인 전까지를 시험했다. 운영 전환은 별도 작업이다.

같은 소스에서 웹 검사 893개, 서버 대화 검사 19개, 기억·대화 저장소 검사 22개, TypeScript 검사와 웹·Rust 빌드를 통과했다. 계획 검증에서 로컬 링크 1,682개를 확인했다. 전체 웹 검사 중 공유 편집창이 먼저 표시되고 가져오기가 뒤늦게 완료되는 경우가 나왔다. 회귀 시험은 가져오기 완료를 기다린 뒤 다른 대화에서는 삽입 버튼이 잠기고 원래 대화에서는 실제로 기존 초안에 글이 붙는지 확인한다.

게이트웨이에서 업무 해석 응답을 모두 읽은 뒤 요청 해시와 결과 종류만 기록한다. 탭 이동으로 브라우저가 응답 본문을 폐기해도 HTTP 200을 잘못된 업무 결과로 집계하지 않는다. [재현 절차](../../deployment/kiri/linux-vm-smoke/README.md#chat-work)
