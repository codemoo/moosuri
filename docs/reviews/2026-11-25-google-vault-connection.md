# 볼트에서 Google 로그인과 Workspace 연결

운영 회원 대화에서 시작한 새 Kiri Chrome은 Google의 비밀번호 화면에 도달했고 브릿지는 `needs_human/sign_in_required`를 기록했다. 설치 관리자 응답에서 콜백 주소가 맞고 웹 클라이언트가 미등록인 것을 확인했다. 이 시점에 Gmail과 Workspace 회원 상태 조회는 각각 404였고 API 읽기는 0건이었다.

| Linux 검증 경로 | 확인한 결과 |
| --- | --- |
| 대화에서 연결 요청 | 데스크톱·휴대폰 폭에서 GWS, Gmail, Drive 요청은 지정한 화면을 열었다. 화면 이동 중 Google 권한 요청과 받은편지함 조회는 발생하지 않았다. |
| 관리자 파일 등록 | 데스크톱 클라이언트, 다른 콜백, 불완전한 파일은 브라우저에서 거절했다. 일치하는 합성 웹 클라이언트는 설치 설정에 제출했다. |
| 볼트 항목 선택 | 회원 이메일 및 공식 HTTPS origin의 일치 여부를 검사했다. 중복 항목은 선택지로 남기고 HTTP, 유사 도메인, 사용자 정보가 있는 URL과 다른 포트는 제외했다. |
| Chrome 비밀번호 입력 | 실제 Linux Chromium에서 확장을 설치하고 키보드로 브라우저 동작을 실행했다. 네트워크를 차단한 합성 화면에서 올바른 계정의 입력란에 한 번만 채웠다. 다른 계정·유사 도메인·추가 인증·복수 입력란·문서 교체는 입력을 중단했다. |
| 회원 권한 저장 | 실제 회원 저장소와 합성 공급자로 계정 일치 승인, 불일치 거절 및 기존 연결 보존, 일반 경로의 다른 계정 선택을 확인했다. |

회원 화면 33건, 볼트 화면·워커 19건, 회원 OAuth 34건, 기존 스키마 이전 4건이 Linux에서 통과했다. 두 화면 폭에서 각각 4개의 브라우저 흐름을 확인했고, Chrome 확장 6개 시나리오는 Linux Chromium과 합성 Google 화면에서 실행했다. [브라우저 시나리오](../../deployment/kiri/linux-vm-smoke/member-ui-scenarios.py) · [확장 시나리오](../../deployment/browser/google-autofill/scenarios.py)

## 운영 배포와 실계정 결과

운영 회원 쓰기를 멈추고 개인 볼륨·볼트와 설정의 복구 사본을 대조했다. 같은 UID, 테넌트, 마운트와 컨테이너 실행 인자로 새 회원 이미지를 기동했다. 회원 DB가 스키마 101에서 102로 올라갔고 기존 대화·권한·볼트 항목 수가 유지됐다. 운영 게이트웨이와 수명주기 서비스, 회원 실행 파일의 SHA-256은 `50cdd810613d4c82c0cf8d474e2d381b3352c3d4eb7c5a199f134b9094ee5da4`, 볼트 서비스는 `558a722eabb0f620ab1753bbca6fe2d7ea88d25650ee2a2ecabaca91df04f57f`다.

기존 이전 점검 도구가 스키마 102를 인식하도록 갱신했다. Linux에서 합성 스키마의 회원 테이블 242개와 회원 소유권에 영향을 주는 외래키 관계 248개를 검사했다. 새 계정 선택 행의 회원은 원래 OAuth 요청에서 확인한다. [스키마 점검](../../audit/account-runtime-inventory.md)

공개 HTTPS로 내려받은 회원 화면 파일 47개와 볼트 파일 6개가 Linux 시험 빌드와 일치했다. 볼트의 `/google-autofill.zip`은 `application/zip`으로 제공되고 manifest는 운영 볼트 주소 한 곳만 허용한다. 기존 회원 데이터와 GWS 릴레이가 준비 상태인지 새 컨테이너에서 다시 확인했다. Linux의 새 브라우저에서 운영 설정 링크를 열면 회원 로그인 화면이 보였고, 로그인 전 설정·GWS 상태·볼트 세션 응답은 각각 HTTP 401이었다.

배포 뒤 등록 회원 이메일로 별도의 새 Linux Kiri Chrome에서 Google 인증을 한 번 더 시작했다. `needs_human / provider_sign_in_required`가 반환됐고 인증 세션은 발급되지 않았다. 회원 볼트에서 실제 Google 비밀번호를 제출한 횟수와 회원 커넥터가 Google API 조회에 성공한 횟수는 모두 0회였다. 운영 회원의 GWS 앱과 Google 권한도 각각 0개였다.

실계정 검증을 재개하려면 소유자가 로그인한 무수리 회원 브라우저 세션과 이 설치의 HTTPS 콜백을 등록한 Google 웹 클라이언트가 필요하다. 회원이 공식 Google 화면에서 승인한 뒤 동일한 회원에게 저장된 계정과 실제 GWS 읽기 응답을 대조한다. [운영 커넥터 안내](../../deployment/kiri/google.md)

저장소 전체의 `cargo fmt --all --check`는 이전 커밋의 Rust 파일 7개에서 차이를 보고했다. 이번 변경에 포함된 Rust 파일은 모두 형식 검사에서 일치했다.
