# 11월 25일 회원 볼트와 대화에서 시작한 Google 로그인

회원은 **연결 → 암호 볼트 → 볼트 열기**에서 별도 창을 열고 그 창에서 잠금을 해제한다. 대화에 **구글 로그인 해줘**라고 쓰면 등록된 회원의 새 Kiri Chrome 프로필로 인증을 시작한다. 두 업무는 각각 원래 회원 세션에서 접근할 수 있다. [볼트 사용법](../../deployment/kiri/README.md#개인-암호-볼트-연결) · [브라우저 사용법](../../deployment/kiri/browser.md#로그인과-google-계정)

## 운영 회원 확인

Linux에서 회원 게이트웨이·브로커·회원 이미지를 교체하기 전에 게이트웨이를 정지하고 복구 사본을 만들었다. 첫 시도에서 릴레이 소켓이 준비되지 않아 트래픽을 다시 열기 전에 복원했다. 두 번째 절체는 소켓 준비와 전용 로그인 경로를 확인한 뒤 완료했다. 기존 회원·테넌트·UID·마운트가 일치했고 공개 HTTPS에서 회원 로그인, 볼트 인계와 소유자 확인을 통과했다. 회원 실행본 SHA-256은 `2d7443e2bd1aba44db0fd46e27efa2f77c299b3fd46cd8f2773379f83622dd9f`다.

운영 Linux Chromium에서 회원이 연결 화면의 볼트 열기를 눌러 별도 HTTPS 창의 잠금 화면을 확인했다. 같은 회원의 대화에서 보낸 첫 Google 로그인 요청은 한 번 접수됐고 Kiri 소켓까지 전달됐다. 원래 작업에는 `browser_google_unknown`, 호스트 영수증에는 `unavailable/bridge_error`가 남았다. 조사 결과 전용 VM의 도우미는 비밀번호 프레임을 요청할 수 있는 과거 버전이었다. 인증 결과로 이 원인을 단정할 수 없어 첫 작업의 결과는 그대로 보존했다.

전용 VM에 `kiri-chrome`의 현재 로그인 도우미를 반영했다. 두 설치 파일의 SHA-256과 프로필 정리 타이머를 확인했다. 설치된 도우미로 합성 화면 여섯 개를 실행해 계정 일치, 계정 불일치, 브라우저 거절, 비밀번호 요구, 사람 확인, 예상 밖 출처를 구별했다. 이 시험에서 Google에 회원의 이메일을 다시 제출하지 않았다.

운영 볼트의 가져오기는 회원 기기에서 지정한 사용자 이름으로 선별해 암호화했다. 항목별로 운영 서버의 커밋 영수증과 저장 상태를 확인했다. 새 클라이언트를 복구 키로 열어 전체 항목의 제목·사용자 이름·URL·메모·암호를 원본과 대조했다. 원본에 OTPAuth가 있던 모든 항목은 서로 다른 두 시각에 별도 HMAC 구현과 코드가 일치했다. 다시 잠금 암호로 연 클라이언트에서 원본 전체가 중복이었고 추가할 항목은 0개였다. 개인 파일과 계정 식별값은 이 기록에 포함하지 않았다.

운영 볼트 서비스만 재시작한 뒤 새 회원 세션으로 인계받아 저장된 항목 수를 다시 확인했다. 공개 HTTPS의 HTML과 JavaScript·CSS·WASM 파일 네 개가 Linux 시험본과 일치했다. 이 볼트 실행본의 SHA-256은 `9d2519f32b3eb1ce1d718db75f00abe40a50eb073b1076b370689907a0e5d31c`다.
