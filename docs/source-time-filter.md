# Search by a source's recorded observation time

In **자료 검색 → 검색 조건**, set **기록 시각 시작 (포함)** and/or **기록 시각 종료 (미포함)**. Inputs use the device's local timezone and are sent as Unix seconds. A start includes that instant; an end excludes it. An empty end or start leaves that side open. The existing **유효 기준 시각** separately chooses when the source's assertion is valid. These two kinds of time are independent: a source recorded in November can describe a fact valid in October.

The authenticated `POST /api/v1/knowledge/search` and native `knowledge_search` read tool accept optional `observed_from` and `observed_until` fields for `kind:"source"`. Both are Unix seconds within year1 through9999; when both exist, start must be earlier than end. The API has no mixed source/memory query kind. Memory searches reject nonnull observation bounds; their existing `valid_at` behavior is unchanged. Missing/null bounds retain the existing search behavior and absent fields retain the old query serialization/cursor identity. Each continuation is bound to the exact range, all other query fields, owner and knowledge generation. A new range needs a fresh search.

A source already requires its explicit `observed_at`; ingestion rejects a missing timestamp rather than substituting validity or the server clock. These timestamps are producer/owner-reported observation metadata, not independent proof of when an event happened. Existing collection/speaker filters, current revision, source deletion, collection withdrawal and account boundaries still apply. Search hits retain their existing projection; opening a source shows its actual recorded observation timestamp.

The read tool uses these fields only for an explicitly requested source-record period. It does not gain date inference, access to another account or a scheduling capability. Date-bound source searches are intentionally ineligible as reusable source-learning proofs and as evidence-calculation bindings, because those learned routes currently have no structural binding for fresh observation ranges. They cannot silently embed a private fixed date into reusable/exported recipes. Unfiltered legacy proofs and source routes remain compatible, with no capability-generation bump, SQL migration or dependency change.

See [source and memory lifetimes](knowledge.md) and [verification](reviews/2026-11-15-source-time-filter.md). This unit supplies explicit source timestamp filtering; it does not complete every F22 retrieval requirement or certify natural-language date interpretation.
