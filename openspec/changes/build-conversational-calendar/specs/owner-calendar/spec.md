## MODIFIED Requirements

### Requirement: Explicit owner Calendar authority
The system SHALL preserve independent owner Calendar consent, fixed Google origin, primary owner
eligibility, attendee-free timed nonrecurring default-event write checks, exact ETags and the
existing direct-form action contract. A newly submitted ordinary chat MAY admit bounded Calendar
reads and one clear current authenticated user's immediate create/update/delete request through a
separate schema30 profile and sealed plan. Retrieved content, history, media, prior runs, skills and
mission templates SHALL NOT create Calendar mutation authority.

#### Scenario: Clear create now with future event time
- **WHEN** the current user requests one eligible event with exact title, explicit date, start and
  end/duration and a unique connected account
- **THEN** the single shared isolated interpretation round proposes its Calendar domain
- **AND** Store verifies frozen clock/original-session authority and seals one fixed action UUID
- **AND** there is no routine approval screen and exactly one provider write invocation.

#### Scenario: Missing duration or incomplete target coverage
- **WHEN** an event lacks an explicit end/duration, or target list coverage is partial/duplicate
- **THEN** the system clarifies and performs no Calendar write.

#### Scenario: Lost acknowledgement or revoked delivery
- **WHEN** dispatch has committed and the provider response is missing or chat authority is revoked
- **THEN** the same action retains minimal receipt/uncertainty and is never resent
- **AND** exact lookup may confirm matching create/update or current delete absence only.

#### Scenario: Withdrawal and immutable older grants
- **WHEN** Calendar disconnect/reconnect, app revision replacement or restore withdraws a grant
- **THEN** direct and inherited Calendar-derived output and private capabilities are purged
- **AND** minimum external-action receipts remain, with no automatic restored execution.
- **WHEN** a run or mission predates schema30 or has media/mission scope
- **THEN** it acquires no new Calendar rights by retry or catalog update.

#### Scenario: Read paging and persistence boundary
- **WHEN** chat lists primary events
- **THEN** a real provider page has at most five events and continuation requires actual same-range
  page lineage; a partial page proves neither global absence nor uniqueness.
- **AND** exact event reads require an opaque same-owner/run observation handle.
- **AND** Calendar-derived artifact persistence is blocked until provenance withdrawal is supported.
