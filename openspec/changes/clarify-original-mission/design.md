## Decisions
Use the existing MissionInputRequest/Wait/Reply lifecycle. The original run, acceptance, lease checkpoint, model/profile, six-model/twelve-tool/two-repair counters and original deadline remain authoritative. One wait per supported field and acceptance revision bounds clarification; context is at most4000 characters and choices have2–5 actual receipt observations. Completed reads are reused; no model polling is introduced.

A candidate binds ID, revision/ETag, receipt step and call ID. Store derives its label, rejects invented/duplicate/stale observations, and rechecks before reply/promotion/use. Source selection references a current stored source. Calendar selection requires a previously admitted date move, the original named title, complete observed candidates and the selected exact event ID/ETag; provider preflight still rejects changed or withdrawn targets.

Context is supplied separately from original task authority and never appended to mail/Calendar effect parameter parsing. Arbitrary new effects, accounts, recipients and titles remain outside its authority. Semantic context/criteria require owner review at completion; explicit mechanical checks still run. Source selections must retain the selected original receipt in final evidence.

An action-needed event has no reminder occurrence and creates no schedule. Schema70 makes notification occurrence nullable, preserves notification rowids for existing push scan cursors and generalizes owned source preferences to mission IDs. Existing schedule and recurring-source mute semantics remain. Push payload stays generic IDs; passive authorization returns only a bounded current mission ID header for navigation. Clicks reauthorize and the app fences messages by account ID. Answer, expiry, cancellation or withdrawal suppress current display/dispatch; a push already accepted by a service cannot be recalled.

Restore includes schema70, then clears input waits/replies and quarantines unfinished grants using the existing restore flow. SQLite table replacement runs atomically with FK enforcement temporarily disabled outside the transaction, then reenables and checks every relationship before Store admission or publication of the private restore stage.
