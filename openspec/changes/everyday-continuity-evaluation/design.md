## Boundaries

Owner-visible synthetic fixture data is public and separate from grader code.
The scripted compatible endpoint receives actual agent requests and derives
arithmetic from actual tool results. The driver only injects authorized owner
messages and controlled transport barriers. SQLite observations remain read-only
and evaluator-only. Existing explicit user acceptance checks are product inputs,
not a channel for hidden grader facts.

## Three complete paths

In-flight guidance holds the final provider response after a search, read and
calculation; HTTP instruction ACK/replay precede one same-run continuation.
Clarification pauses after a real saved read, reopens the world while waiting,
then answers the original wait and preserves the original run/acceptance.
Free context requires partial/owner-review even if arithmetic checks pass.
Reminder controls use the preceding same-thread real receipt with a decoy reminder
present; exact replay preserves the original run and revisions.

## Stage accounting

Plans are created before execution. Each entered stage starts as failed until
bounded execution and observations establish its postconditions. Later stages
stay not_run on early exit. Model dispatches come from the loopback provider
ledger, saved tool calls from SQLite. Zero-call stages enforce ACK/wait/replay
contracts. Row failure does not remove eligibility or planned cases. Missing
usage is never inferred from nominal fixture token counts.

## Independent rejection

Mutants alter observed receipts, original work, completion state, reminder
identity or replay identity. Every case must first pass its own positive control.
Grading uses factual totals and shipping, saved tool receipts, owner identities,
acceptance, revision and state transitions rather than exact final prose.
