# Design

Extend existing Rust core/Store/Runtime and React cards over SQLite. Reuse mission/run identity, versioned profiles, tool/child receipts, artifact/mail/Calendar services and native broker journals. Do not add a workflow server, second queue, unrestricted code interpreter, credential-bearing generic connector or new approval ledger.

The [canonical implementation plan](../../../docs/additional-capabilities-plan.md) defines A–F ownership, dependencies, actual-source gaps, checks and deferred scope. First implement A's requested read→private-report flow; B's account descriptors can be developed independently and integrated with the same step identity. C adds native read grants; D composes existing actions; E qualifies already-working structures; F is a separate browser adapter boundary.

Owner-visible plans retain at most five stages; supported recipes allow at most eight nodes and nine tool kinds. Real leaf dispatches share the current six-model/twelve-tool and mission two-repair limits. Preserve per-mode deadlines: ordinary chat120seconds from first dispatch, missions their original maximum-day expiry. Do not introduce an undocumented active-time reset or automatically renew a wait. Two waiting parents plus one runnable/explicitly paused parent per owner, sixteen unfinished installation-wide and one executing mission are proposed initial admission bounds. Waiting releases execution slots, not accounting or request identity.

Ready waits retain their status while capacity is occupied. The writer atomically promotes at most one valid ready parent in original admission order when its owner slot is free. Direct/recurring admission and resume share capacity predicates; slot release and the existing due loop retry promotion. Explicit pause retains occupancy until owner action or expiry. Expired ready records are retired without a page visit.

A missing connection may be filled only through a typed unresolved slot fixed at original admission, with an implemented/versioned operation, actual model/tool probe and bounded operation/resource/account-selection constraints. Current owner/device/grant validation fills only that slot. Setup never rebuilds the whole profile or adds a tool/schema/permission; old runs without such a slot require a fresh explicit request after setup.

Existing display-only native Gmail records stay excluded from model context, recall, reports and learning. New model-readable operations need a separate device grant, result type and provenance/invalidation path. Credentials stay local; approved content may enter the selected model. Server-managed OAuth and native-vault execution remain visibly different modes.

New writes reuse domain idempotency/CAS/receipt behavior. Mail approval binds exact current content/account/recipient/timing; an expired reasoning run may not restart because a prepared MailAction is later approved. Calendar remains current-owner primary solo-event scope. Recipes never carry approval, account bindings, old source values or authority to add tools. Unknown external effects remain pinned to their original device/action and are reconciled without redispatch.

Schema additions migrate normal-open and sealed restore together, preserve completed history and quarantine restored waits/grants. Old textual plans, unsigned descriptors, imported samples and legacy display records cannot gain authority through migration. Native wire changes use explicit compatibility versions and retain signed bytes. CI remains disabled; each user-visible delivery includes focused outcomes, independent boundary review, docs/status and commit/push.
