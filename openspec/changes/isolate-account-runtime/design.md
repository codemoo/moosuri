# Kiri 기반 사용자별 무수리 설계

2026-11-19 검토. 기준은 dev.30, SQLite schema 81이다. **Linux 서버가 유일하게 상시 켜 둘 기기**다. 사용자 한 명에게 하나의 논리적 비서와 하나의 실행 컨테이너를 할당한다. 업데이트로 컨테이너 ID가 바뀌어도 비서 ID와 데이터 볼륨은 유지한다.

## 1. 현재 코드에서 달라지는 경계

현재 `Store::open_admitted`는 설치 데이터 폴더에서 `assistant.sqlite`와 쓰기 잠금, 복구 저널, 공급자 암호화 키를 함께 연다. 계정·세션·작업은 같은 DB에서 소유자로 구분된다. 별도 데이터 폴더로 기존 `serve`를 계정 수만큼 실행하면 각각이 독립 설치로 초기화된다. 기존 폴더를 복제하면 다른 사용자의 데이터와 설치 키도 함께 복제된다. 먼저 설치 단위와 사용자 단위의 저장·실행 인터페이스를 분리해야 한다. 여기서 공용 모델의 **읽기 전용 사용**은 인증된 모델을 호출할 수 있다는 뜻이다. 읽기 전용 파일에 원본 API 키나 구독 토큰을 넣으면 임의의 스킬도 읽어 복사할 수 있다. 실제 키 파일은 공용 모델 서비스에만 두고, 사용자 컨테이너는 자신의 Unix 소켓 또는 짧은 수명의 서비스 권한으로 호출한다. 키 회전이나 구독 재로그인은 한 곳에서 처리한다. 모델 서비스는 요청을 전달하는 동안 필요한 프롬프트와 응답을 보지만 대화 기록·도구 결과·CLI 세션을 공용 HOME이나 로그에 저장하지 않는다. 모델 도구 요청은 원래 사용자의 컨테이너로 반환하고 그곳에서 권한과 실행을 결정한다.

구독 CLI가 인증·대화·캐시를 같은 파일에 섞어 쓰면 우선 합성 사용자 둘로 동시 로그인 갱신과 기록 분리를 검증한다. 공급자가 허용하는 구독 사용 조건도 확인한다. 분리가 검증되지 않은 어댑터는 공용 카탈로그에서 비활성 상태로 표시하며, 검증된 API·로컬 어댑터로 먼저 출시할 수 있다. 기존 사용자의 개인 구독·API 키는 공용으로 자동 전환하지 않는다. 설치 관리자가 명시적으로 공용 연결을 만들고 해당 사용자가 모델 선택을 옮길 때까지 기존 바인딩의 소유권을 유지한다.

공용 인증의 갱신은 연결별 단일 작성자가 맡는다. 공급자의 대화 ID·업로드 파일 ID·CLI 세션/캐시·재개 식별자는 소유자, 연결 버전, 로컬 대화·실행에 묶어 개인 런타임에만 영속화한다. 같은 인증 HOME을 여러 사용자 CLI에 직접 열어주지 않는다. 기존 ChatGPT 인증 봉인이 runtime/host/binding과 토큰 세대에 묶인 경우 단순 키 교체로 이식됐다고 판정하지 않는다. 원래 소유자의 연결과 선택 모델·강도의 대화/도구/이미지 실행 증명을 재검증하고 필요한 사용자만 다시 로그인한다.

스토어 분리 후에는 공용 사용량 예약과 개인 작업 접수가 하나의 SQLite 트랜잭션에 들어가지 않는다. 개인 DB가 안정적인 호출 ID를 먼저 기록하고 공용 서비스는 계정·활성 세대·연결 버전·예산을 검증한 뒤 같은 ID에 한 번만 예약한다. 완료 영수증으로 한 번만 정산하고 응답이 유실되면 같은 ID의 상태를 조회한다. 결과가 불명인 공급자 호출을 자동 반복하지 않는다. 개인 볼륨 복원으로 공용 지출 원장을 되감지 않는다. 계정 정지·절체 시 공용 호출과 외부 통신 게이트에서 세대를 철회하고, 사용자 러너 정지 확인 전까지 관리자에게 ‘정지 중’으로 표시한다. 진행 중 외부 요청은 이미 전달됐을 수 있으므로 영수증을 대조한다.

## 2. 사용자가 거치는 흐름

1. **가입과 로그인.** 설치 시 관리자 계정과 개인 볼륨을 만들고, 초대할 때 회원의 비서를 미리 준비한다. 관리자가 발급을 요청하면 사용자 컨테이너에서 임시 비밀번호를 생성하고 한 번만 전달한다. 비밀번호 검증·강제 변경·세션 발급·로그아웃은 그 컨테이너가 맡는다. 로그인 주소와 PWA 설치 주소는 하나다.
2. **라우팅과 세션.** 첫 로그인은 이메일 인덱스로 대상 컨테이너를 찾는다. 이후에는 서명된 불투명 라우팅 값으로 컨테이너만 고르고, 실제 쿠키와 인증 세대는 컨테이너가 검증한다. 게이트웨이가 TLS와 전달 중인 쿠키를 다루므로 요청 본문·쿠키 로그를 끈다. 클라이언트가 전송한 계정 ID를 라우팅 권한으로 인정하지 않는다. 정지·삭제 시 기존 SSE, 백그라운드 실행 및 공용 모델 호출도 철회한다. PWA 계정 전환 시 이전 계정의 개인 캐시·푸시 구독을 분리한다.
3. **Gmail 연결.** 설치 관리자가 Google 웹 OAuth 앱과 콜백을 한 번 등록한다. 회원은 채팅에서 **Google로 연결**을 누르고 Google 화면에서 자신의 계정에 동의한다. 고정된 서버 콜백은 서명·만료가 있는 라우팅 정보로 원래 컨테이너에 전달한다. 컨테이너가 원래 세션, 일회성 state, PKCE를 검증하고 토큰 교환·암호화 저장·갱신·철회를 담당한다. 조회·수집은 서버의 해당 컨테이너에서 실행한다. GWS CLI를 선택해도 실행 파일만 공유하고 인증 디렉터리는 개인 볼륨에 둔다.
4. **대화와 업무.** 연결을 시작한 사용자의 최신 메일 조회는 같은 대화에서 한 번만 이어간다. 새 지침이나 새 요청이 도착했으면 기존 재개 규칙을 따른다. 본문 검색·예약·발송으로 권한을 확장하지 않는다. 메일 발송은 최종 미리보기 승인 뒤 처리한다. 작업 상태와 결과는 전용 볼륨에 기록하고, 앱 재실행 시 마지막 이벤트부터 이어받는다.
5. **무인 운영.** 첫 버전은 활성 계정의 컨테이너를 상시 실행한다. 앱을 닫아도 예약·메일/Slack 수집·사용자가 등록한 커스텀 수집·푸시가 계속된다. 컨테이너 안 스케줄러가 다음 기한까지 대기하며, 호스트 재시작 시 지속된 커서와 미실행 회차를 기준으로 복구한다. Telegram은 봇 토큰당 수신자 한 곳만 두고, 공유 봇이면 최소 라우팅 서비스가 업데이트를 검증해 소유 컨테이너에 전달한다. 개인 연결·대화·업데이트 중복 제거 원장은 계정 내부에 둔다. 단일 poller는 소유자 전용 영속 수신함에 update ID와 내용을 기록했다는 ACK를 받은 뒤에만 연속된 중앙 offset을 전진시킨다. ACK 유실 시 같은 ID를 재전달하고 오프라인 회원의 컨테이너는 깨워서 접수한다. 기한 내 저장할 수 없는 경우 Telegram 보존 기한에 따른 유실 가능성을 운영자에게 표시한다. 중앙에는 원문을 보관하지 않는다. 사용자가 별도 봇을 쓰면 해당 컨테이너가 직접 수신한다.

## 3. Kiri 적합성 검토

Kiri는 무수리 호스트에 설치하는 OCI 컨테이너 엔진이다. Linux에서는 호스트 커널을 공유한다. 공식 Linux 문서는 systemd, `kiri-lite`, `/run/kiri/docker.sock`을 설명한다. 확인한 릴리스 v0.2.1에는 amd64·arm64 Linux용 lite DEB/RPM이 올라와 있다. 소개 페이지 일부의 “coming soon” 표기와 달라 배포물은 릴리스 기준으로 기록했다. 저장소 라이선스는 Apache-2.0이며 번들 의존성 고지는 패키지별로 확인한다. [Linux 문서](https://docs.runkiri.com/linux/) · [v0.2.1 릴리스](https://github.com/libracoder/kiri/releases/tag/v0.2.1) · [라이선스](https://github.com/libracoder/kiri/blob/v0.2.1/LICENSE)

Docker Engine API 호환과 named volume, 네트워크, 자원 제한, 재시작 정책이 문서화돼 있다. 무수리는 만들기·조회·시작·정지·상태 확인·재생성에 필요한 호출만 버전별로 검증한다. 묵살되는 옵션도 있을 수 있어 응답 코드와 inspect 값 외에 실제 파일 접근·연결·재부팅 결과를 확인한다. 공급사의 Mac 시작시간 벤치마크는 무수리 Linux의 용량·응답시간 근거로 쓰지 않는다. [컨테이너](https://docs.runkiri.com/docker/containers/) · [스토리지](https://docs.runkiri.com/docker/storage/) · [네트워크](https://docs.runkiri.com/docker/network/)

`kiri` 그룹은 호스트 root에 준하는 권한을 갖는다. 제어 소켓은 프로비저너만 열고, 사용자 요청으로 이미지·마운트·호스트 경로·포트·실행 인수를 임의 지정할 수 없게 한다. 공통 이미지에 비루트 UID, 읽기 전용 루트, 최소 권한, CPU·메모리·PID 한도와 사용자별 디스크 한도를 적용한다. 표준 피처가 없는 한도는 호스트 볼륨 쿼터로 검증한다. 외부에 공개할 주소는 기존 무수리와 별도 볼트 주소뿐이다. 개인 컨테이너는 외부 공개 포트 없이 사용자별 소켓으로 연결한다. 인터넷 도구는 계정 간 통신·호스트 관리 주소를 차단하면서 Google·메일·브라우저 작업에 필요한 외부 통신을 허용하는 경로로 구성한다. Kiri Share, 공용 브리지에서의 상호 통신, 호스트 HOME·SSH agent 자동 공유를 사용하지 않는다. [Linux 소켓 권한](https://docs.runkiri.com/linux/) · [Kiri 보안 모델](https://docs.runkiri.com/security/)

같은 호스트의 root는 실행 중 프로세스와 일반 볼륨을 관찰할 수 있다. 사용자 컨테이너 격리로 보장할 범위는 다른 회원과 일반 관리자 웹 기능으로부터의 분리다. 볼트의 관리자 비가독성은 계속 클라이언트 암호화로 보장한다. 개인 컨테이너 안에서 수행되는 모든 작업이 호스트 관리자에게도 보이지 않는다는 보장은 하지 않는다.

공개 소스 검토에서 확인한 제약도 있다. Engine API는 부분 구현이며, 조사한 컨테이너 생성 경로에서 사용자 네임스페이스 UID 재매핑과 AppArmor/SELinux 프로필 강제를 확인하지 못했다. `--internal`은 기본 경로 제거를 뜻하며 호스트 게이트웨이 접근 차단까지 입증하지 않는다. named volume의 local driver도 호스트 디렉터리를 바인드할 수 있다. 프로비저너는 사전에 정한 마운트만 생성하고 임의 driver 옵션을 받지 않는다. 재시작 정책은 프로세스를 새로 띄우므로 진행 중인 작업은 무수리의 저널에서 복구한다. Linux 시스템 패키지 자체도 빌드·설치 검증 대상이다. ## 4. 이전과 복구

- **무엇을 분리할지 먼저 확정한다.** schema 81의 테이블·외래 키, 파일·인덱스, 암호화 키, 감사·복구 저널을 설치 공통/계정 전용/재생성/재인증 대상으로 전수 분류한다. `AccountId`와 `TenantId`는 각각 보존한다. 이메일로 새 소유자를 추정하지 않는다. 자식 행에 소유자 ID가 없으면 부모 참조를 따라 검증한다. 연결·모델 선택의 기록, 소유권, 외부 영수증 누락은 전환 실패다. 기존 기록은 확인되지만 인증 비밀을 안전하게 옮길 수 없는 항목은 그 사용자에게 재인증 대기로 표시한다.
- **정상 이전과 재해 복구를 분리한다.** 현행 백업은 의도적으로 공급자 키를 제외하고 Push와 Telegram을 격리한다. 복구 시 세션과 일부 토큰·선택을 무효화한다. 기존 백업을 사용자 수만큼 복원하는 방법으로는 요구사항을 만족할 수 없다. 정상 이전에는 소유자별 추출·재암호화·검증기를 만들고 이전 원본 DB는 보관한다. 공용 루트 키를 개인 볼륨에 복제하지 않는다. 합성 표본으로 바인딩의 암호학적 동일성과 scope를 입증할 수 없는 항목만 재로그인을 요청한다. [백업](../../../docs/backup.md) · [복구](../../../docs/restore.md)
- **기존 세션과 진행 중 작업.** 기존 쿠키에는 새 컨테이너의 라우팅 힌트가 없을 수 있다. 전환 기간엔 기존 인증기가 유효한 세션에 한해 짧은 일회성 전달권을 발행하고 새 컨테이너가 로컬 세션을 재발급한다. 전달권은 브라우저·계정·양쪽 세대에 묶고 사용 후 폐기한다. 이전하지 못하는 로그인은 해당 사용자만 재인증한다. 신규 가입부터는 이 과도 경로를 사용하지 않는다.
- **계정 단위 절체.** 대상 계정의 신규 쓰기·스케줄 claim·메일 발송을 기존 러너에서 차단한다. 수신 중인 이벤트와 이미 승인된 외부 작업을 drain하고 watermark를 기록한다. 새 볼륨에서 SQLite 무결성, 외래 키, 참조한 파일 해시, 세션/예약/수집 커서, 저널 연속성과 볼트 소유권을 검사한다. 변경 스트림은 소유 컨테이너 하나만 쓰도록 세대 번호와 임대 토큰으로 차단한다. 라우팅 전환 후 스트림은 마지막 이벤트 ID에서 재개한다. 이미 전송됐는지 모르는 메일은 자동 재발송하지 않는다.
- **롤백.** 새 컨테이너에서 사용자 쓰기를 받기 전에는 새 러너를 정지하고 원래 세대로 되돌릴 수 있다. 쓰기나 외부 작업이 발생한 뒤에는 양쪽 러너를 차단하고 최신 저널·영수증과 커서를 대조한 뒤 앞으로 복구하거나 검증된 역이전을 수행한다. 과거 DB로 트래픽만 돌려 중복 발송하는 롤백은 허용하지 않는다.
- **운영 수명주기.** `provisioning → ready → draining → stopped`를 설치 서비스에서 추적한다. 같은 계정 초대·재시작 요청을 반복해도 컨테이너가 두 개 실행되지 않게 한다. 이미지 교체 전 계정별 암호화 백업을 만들고, 다른 볼륨에 복원 시험을 한다. 볼트의 어댑터는 계정 세션·세대 검증을 해당 컨테이너에 위임하도록 변경하고 별도 출처·키와 독립 복구 절차를 유지한다. 정지는 볼륨을 보존한다. 실제 삭제는 기존 삭제 확인·보존 정책을 따르며 볼륨, 인덱스, 전용 키, 외부 연결 철회와 백업 만료까지 추적한다. [계정 관리](../../../docs/account-management.md) · [별도 볼트](../../../docs/vault-service-client.md)

## 5. 진행 순서와 채택 기준

| 단계 | 결과물 | 다음 단계로 넘어가는 기준 |
|---|---|---|
| 0. Linux 적합성 실험 | 운영과 분리된 Linux에 릴리스 digest를 고정한 Kiri와 합성 계정 A·B를 띄운다. 일반 사용자의 PC에는 설치하지 않는다 | 두 계정이 상대 파일·소켓·내부 서비스와 엔진 소켓을 열 수 없어야 한다. 읽기 전용 공유물, 제한 초과 동작, 네트워크·볼륨 보존, 데몬 재시작·호스트 재부팅을 관찰한다. 핵심 격리나 복구가 불가능하면 채택을 보류하고 해당 근거를 기록한다 |
