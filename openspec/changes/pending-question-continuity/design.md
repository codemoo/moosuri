# Design

`request_continuations` shares the immediate previous completed-run lookup and
pending context eligibility between inheritance and local question cancellation.
The existing thread/account/session/epoch/model, invalidation, Calendar profile and
original expiry checks remain mandatory.

An ambiguous response can retain only an already established machine field whose
typed value is still absent, or whose existing `time` gap is an unresolved timezone
for Calendar or a local-clock mission. The existing source-zone validator checks
the bounded literal lineage against frozen admission metadata; relative/interval
mission times do not acquire a new timezone requirement. It cannot create a new
continuation from an ambiguous initial request, replace a complete field or turn a selected target back into a
missing value. The raw acknowledged decision remains unchanged; display resolves
its question through the saved pending-field identity. Literal answer history,
32KiB/four-answer limits and original expiry remain unchanged.

After existing supported-profile/media/personal/selected-target validation and
before a new mission chat plan is inserted, a whole literal generic cancellation
reply can retire the immediate pending question and complete the current chat.
This creates no model call, action grant or domain control receipt. Original saved
work remains intact. Existing request-ID replay returns the same stored chat.
Generic cancellation grammar is shared with reminder drafts; `cancel reminder`
remains reminder-specific. Named targets, quoted/conditional replies and composite
cancel-plus-new-task requests do not match. A separate following explicit request
uses its own ordinary current-user admission. Composite cancellation/new-action
interpretation is outside this change.

No schema/DTO migration, Calendar effect expansion, general history authority,
mail approval change or new permission prompt is introduced. Replaying old stored
clarification payloads keeps their original finite/prose compatibility and fallback.
